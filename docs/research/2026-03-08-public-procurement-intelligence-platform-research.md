## 1. Executive Summary

### Feature Overview

The product is a procurement intelligence platform for UK public-sector contracts. It should ingest official contract notice data every day, normalize and store it, qualify it for relevance to physical-goods supply opportunities, enrich qualified notices with supplier pricing plus landed-cost estimates, surface high-margin opportunities in a dashboard, and optionally launch semi-automated bidding workflows using agent skills and browser automation.

This is not one system. It is four tightly connected systems:

1. Procurement ingestion.
2. Intelligence enrichment and margin estimation.
3. User-facing review and decision dashboard.
4. Agent-assisted bidding workflow execution.

### Key Recommendations

- **Primary data strategy:** Use official procurement APIs/OCDS feeds first, not generic scraping.
- **System of record:** Use hosted PostgreSQL via Supabase, not SpacetimeDB or Convex, for the core control plane.
- **Desktop/runtime architecture:** Use Tauri v2 with a Rust daemon/sidecar for local agent execution.
- **Frontend strategy:** Do not force a single SSR-style Next app inside Tauri. Use a shared React UI package with a static desktop shell and a separate web surface if needed.
- **Cost-estimation engine:** Build an internal landed-cost engine backed by HMRC Trade Tariff, HMRC customs valuation rules, Xe FX, and freight-market APIs.
- **Agent orchestration:** Use Codex/Claude CLI non-interactively as child processes with skills and kickoff prompts. Do not make PTY emulation the first implementation.
- **Automation policy:** Keep human approval in the loop for HS-code confidence failures, weak supplier matches, and all bid submissions until portal-specific playbooks prove stable.

### Primary Recommendation in One Sentence

Build a greenfield monorepo around official OCDS procurement connectors, a Supabase/Postgres shared control plane, a Rust local execution daemon, and an internal confidence-scored landed-cost engine that uses agents as specialized workers rather than as the orchestration layer.

### Critical Decisions Required

1. Whether MVP scope is England/Wales/Northern Ireland only or full UK coverage including Scotland-specific procurement flows.
2. Whether the first release should optimize for desktop-first operators or equal desktop/web parity.
3. How much autonomy is acceptable in bidding workflows before manual review is mandatory.
4. Whether the margin model should default to a VAT-recoverable importer-of-record assumption.
5. Whether Chinese supplier pricing is allowed to rely on browser automation when official APIs are insufficient.

2. **Phase B:** Preliminary AI qualification + supplier price enrichment.
3. **Phase C:** Landed-cost engine with customs/logistics and confidence scoring.

### What Will Make or Break the Product

- Reliable notice ingestion is easy compared with supplier-price normalization.
- Supplier-price normalization is easy compared with correct product matching.
- Product matching is easy compared with accurate landed-cost estimation at contract scale.
- Landed-cost estimation is easy compared with legally and operationally safe bid automation.

This means the platform must preserve confidence scores, raw evidence, and manual override points from day one.

## 2. Intent & Requirements Analysis

### 2.1 Problem Statement

**The Problem:**

You want to identify UK public contracts for physical goods where your business can source from lower-cost suppliers, especially China-linked marketplaces or wholesale suppliers, calculate realistic landed cost in GBP, and decide whether the arbitrage margin justifies pursuing the opportunity.

**Why It Matters:**

Without a structured pipeline:

- high-value opportunities remain hidden in noisy procurement feeds,
- manual screening takes too long,
- expiration windows are missed,
- margin calculations are inconsistent,
- bidding effort gets spent on contracts that are not commercially viable.

**Current State:**

There is no implementation yet. The repo is effectively empty, so the research must define the foundational architecture instead of fitting into existing code.

### 2.2 Deep Intent Summary

The user is not asking for a generic contract-search dashboard. The real target is a **lead-qualification and arbitrage intelligence engine** with these business goals:

1. Pull in public contract opportunities daily.
2. Filter to contracts that are still actionable.
3. Filter further to physical-goods opportunities.
4. Estimate whether UK/EU sourcing is materially more expensive than Chinese sourcing.
5. Include logistics, customs, and FX to reach a true landed margin.
6. Present only the contracts worth human attention.
7. Let an operator reject, review, or trigger bid-support automation.

### 2.3 User Stories

```gherkin

So that I do not rely on manual searching across multiple portals
```


```gherkin

```


**Primary User Stories:**

1. As an operator, I want daily ingestion and manual reruns so I can trust pipeline freshness.
2. As an analyst, I want only active goods-based contracts surfaced so I do not waste time on services or near-expiry notices.
3. As a decision-maker, I want landed-cost and net-margin estimates in GBP with evidence so I can decide whether to pursue the opportunity.
4. As an operator, I want clear reject/bid controls and auditable history so contract handling is disciplined.

**Secondary User Stories:**

1. As an administrator, I want skills, prompts, source credentials, and company profile data centrally managed so local agents run consistent workflows.
2. As a compliance-aware operator, I want confidence scores and human-override points so I know when the system is uncertain.

### 2.4 Success Criteria

**Functional Criteria:**

- [ ] Daily ingestion pulls all relevant notices from selected official sources with cursor/date tracking.
- [ ] Contracts expiring within 30 days are automatically excluded from active qualified views.
- [ ] Goods-vs-services classification is available for every normalized contract with evidence and confidence.
- [ ] Supplier-price enrichment stores at least one UK/EU and one China-oriented sourcing estimate for qualified goods contracts where feasible.
- [ ] Landed-cost calculation includes FX, customs duty, import VAT logic, logistics estimate, and confidence metadata.
- [ ] Contracts are only highlighted as final qualified opportunities when estimated net margin exceeds 20% and the estimate confidence clears the review threshold.
- [ ] Every final opportunity has a readable Markdown manifest stored as an artifact.
- [ ] Operators can reject, watch, or start a bid workflow from the dashboard.

**Non-Functional Criteria:**

- [ ] Freshness: due ingestion jobs are enqueued by hosted scheduling within 24 hours of publication cadence, and completed within SLA while at least one healthy executor is online.
- [ ] Reliability: job execution is idempotent and resilient to duplicate local daemons.
- [ ] Explainability: every automated decision stores evidence, source URLs, timestamps, and model confidence.
- [ ] Security: secret-bearing actions run in the daemon, not in the browser.
- [ ] Observability: every ingestion, enrichment, and bidding run is traceable.

### 2.5 Scope Definition

**MVP Scope (Must Have):**

- Official-source procurement ingestion for selected UK sources.
- Normalized notice + contract storage.
- Preliminary qualification by expiry and goods relevance.
- Supplier-price enrichment from selected sources.
- Landed-cost engine with shipping/customs/FX.
- Dashboard for browse/search/review/decision.
- Manifest generation.
- Manual and scheduled execution.
- Portal-specific bid workflow framework, with at least one example implementation.

**Phase 2 (Should Have):**

- More procurement source connectors.
- More supplier marketplaces.
- Better product matching using embeddings + structured attributes.
- Freight broker quote escalation when confidence is low.
- Multi-user collaboration and task assignment.

**Future Consideration (Could Have):**

- Cloud fallback executors when no local executors are online.
- Automated RFQ emails/messages to suppliers.
- Historical win-rate and bid-quality analytics.
- Portfolio optimization across contracts.
- Inventory-aware sourcing recommendations.

### 2.6 Non-Goals & Exclusions

**Explicitly Out of Scope for MVP:**

- Fully autonomous bid submission for all portals.
- Replacing customs brokers or freight forwarders in legally sensitive cases.
- Full ERP/accounting integration.
- Guaranteed exact landed-cost precision for every SKU without human verification.
- Unsupported blanket scraping of marketplaces that prohibit or technically block it.

**Deferred:**

- Invoicing and fulfillment operations after a bid is accepted.
- Full tender drafting beyond structured pre-bid submission support.
- Broad non-UK procurement expansion.

### 2.7 Constraints

- Procurement data is heterogeneous across portals and legal regimes.
- China-oriented supplier APIs are much weaker than UK procurement APIs.
- Customs classification accuracy is business-critical and sometimes legally sensitive.
- Freight estimation depends on shipment mode, Incoterms, density, route, seasonality, and carrier conditions.
- Local daemon execution introduces availability and concurrency concerns.
- Tauri desktop constraints mean server-style Next.js patterns should be avoided in the desktop shell.

### 2.8 Key Ambiguities Identified

| Ambiguity | Why It Matters | Working Assumption |
|-----------|---------------|--------------------|
| Full UK or only non-Scottish procurement in MVP | Source connectors and legal variation differ | Start with England/Wales/NI plus optional PCS connector |
| Exact supplier sources in China | API access and terms differ sharply | Hybrid approach: official APIs where available, browser/manual fallback where necessary |
| Web and desktop parity | Affects frontend architecture | Desktop-first ops experience, web dashboard supported from shared UI |
| Fully automatic bidding or semi-automatic | Major risk and compliance impact | Semi-automatic by default |
| Use of pure local compute | Affects reliability of scheduled ingestion | Shared hosted control plane + local executors + optional cloud fallback later |

### 2.9 Research Direction

Based on the intent analysis, the most important research areas were:

1. Official UK procurement data access because ingestion quality is foundational.
2. Customs and freight estimation because margin decisions depend on landed cost, not ex-works price.
3. Supplier pricing APIs and source constraints because China-side sourcing intelligence is the noisiest part of the system.
4. Desktop/daemon/shared-database architecture because the user explicitly wants local agent execution with centralized storage.
5. Skills and agent CLI orchestration because this is core to the desired workflow model.

### 3.5 Code Patterns to Follow

Because no project code exists, patterns should be created deliberately instead of discovered accidentally.

#### Pattern: Raw payload retention

Every external fetch should store:

- source name,
- endpoint or page URL,
- fetched timestamp,
- raw response payload or storage pointer,
- normalized projection,
- parse confidence and parse version.

This is essential because procurement notices change, supplier prices change, and AI decisions need replayability.

#### Pattern: Confidence-scored enrichment

Every enrichment result should store:

- value,
- method,
- evidence,
- confidence score,
- expiration/TTL,
- manual override fields.

If this is not built into the schema early, the platform will drift into fake precision.

#### Pattern: Orchestration state separate from agent output

Agent skills and manifests should be artifacts. The source of truth for job status, retries, leases, and workflow transitions should stay in database tables. Name the queue generically, because most jobs are workflow jobs, not agent runs.

#### Pattern: Deterministic fallbacks

Use rule-based gating before AI:

- expiry date rule,
- procurement category rule,
- presence/absence of quantity/unit,
- duty/VAT calculation formulas,
- FX snapshot rules.

Reserve AI primarily for:

- goods vs services classification in ambiguous notices,
- product matching,
- extracting structured line items from messy text,
- generating human-readable manifests,
- browser interaction for bid flows.

### 4.2 Procurement Rules and Notice Semantics

#### What changed recently

Find a Tender states that for procurement processes starting on or after **24 February 2025**, notices specified by the Procurement Act 2023 apply, with transitional treatment for earlier processes and jurisdiction-specific exceptions.

**Official references:**

- https://www.find-tender.service.gov.uk/Home/NoticeTypes
- https://www.gov.uk/government/publications/procurement-act-2023-short-guides/central-digital-platform-factsheet-html
- https://www.gov.uk/government/publications/procurement-act-2023-guidance-documents-procure-phase/guidance-central-digital-platform-and-publication-of-information-html

#### Why this matters for the product

- Notice types changed after 24 February 2025.
- Expiry logic cannot depend on one legacy field name.
- Contract lifecycle stages are richer than “tender open” vs “closed”.
- Transitional notices may continue under earlier legislation.

#### Recommendation

Normalize notice lifecycle into internal stages:

- `pipeline`
- `planning`
- `tender_open`
- `award`
- `contract`
- `termination`

Then derive operator-facing eligibility rules from normalized state, not from raw portal-specific labels.

- terms and access rules are reviewed,
- captured evidence is stored,
- failures do not block the whole enrichment pipeline.

#### Supplier Price Intelligence Recommendation

Use a **tiered supplier-source model**:

1. API-first UK sources: eBay, Amazon adapter.
2. Official-but-auth-heavy China sources: Alibaba ecosystem where access is possible.
3. Browser/manual escalation for high-value opportunities only.

Do not flatten these into one “price” field. Every quote needs:

- source,
- region,
- quote class,
- quoted quantity and unit,
- quantity basis,
- unit assumptions,
- MOQ assumptions,
- shipping included or excluded,
- confidence,
- validity window.

For large tenders, marketplace listings should usually be treated as **indicative signals**, not executable procurement offers. Once an opportunity survives early filtering, the system should escalate toward RFQs, negotiated quotes, or supplier-confirmed volume pricing before treating margin as decision-grade.

### 5.2 High-Level Component Design

#### Component: Source Registry

**Responsibility:** Define procurement sources, schedules, connector types, credentials, and status.

**Interface:**

```ts
export interface SourceDefinition {
  id: string;
  kind: "fts" | "contracts_finder" | "pcs" | "html_fallback";
  enabled: boolean;
  pollingMode: "cursor" | "date_window" | "manual";
  baseUrl: string;
  authStrategy: "none" | "api_key" | "oauth" | "session";
  scheduleCron?: string;
}
```

#### Component: Ingestion Runner

**Responsibility:** Pull source data, store raw payloads, normalize notices, emit qualification jobs.

#### Component: Hosted Scheduler

**Responsibility:** Enqueue due jobs independently of desktop availability. This should be implemented in the hosted control plane, for example with `pg_cron` or an equivalent server-side scheduler.

#### Component: Preliminary Qualification Engine

**Responsibility:** Reject near-expiry and non-goods opportunities as early as possible.

#### Component: Product Extraction Engine

**Responsibility:** Convert messy notice text into line items, quantities, unit assumptions, candidate product categories, and CPV/commodity hints.

#### Component: Supplier Quote Engine

**Responsibility:** Fetch or infer comparable supplier prices from UK/EU and China-oriented sources.

#### Component: Landed-Cost Engine

**Responsibility:** Combine ex-works or seller price with freight, duty, VAT, fees, and FX to produce gross and net margin estimates.

#### Component: Manifest Generator

**Responsibility:** Produce human-readable Markdown summarizing the opportunity, assumptions, evidence, and recommendation.

#### Component: Bid Workflow Executor

**Responsibility:** Launch portal-specific agent playbooks after operator approval.

### 5.3 Canonical Workflow

```text
new notice
  -> normalize
  -> dedupe/merge
  -> preliminary qualification
     -> reject if expiry < 30 days
     -> reject if clearly not goods
  -> product extraction
  -> UK/EU supplier pricing
  -> China supplier pricing
  -> gross margin estimate
     -> if gross margin >= 30% and evidence confidence is adequate, continue
     -> if gross margin < 30% but uncertainty is high, route to review instead of hard reject
  -> shipping + customs + FX
  -> net margin estimate
     -> if net margin >= 20% and confidence is adequate, qualify
     -> otherwise keep as review / non-qualified
  -> generate manifest
  -> operator review
     -> reject
     -> watch
     -> bid workflow
```

### 5.6 Ingestion Data Flow

#### Data Flow: Scheduled Ingestion

1. Hosted scheduler inserts due ingestion jobs into `workflow_jobs`.
2. Any healthy local daemon claims a job with a lease.
3. Connector fetches source data using cursor or time window.
4. Raw response is stored.
5. Notices are normalized into internal schema.
6. Dedupe layer maps each notice into a canonical `procurement_processes` record using OCID and source heuristics, but only auto-merges when merge confidence clears a threshold.
7. Qualification jobs are queued for new or materially updated processes, retaining notice-level provenance.

#### Error Cases

- API timeout -> retry with exponential backoff.
- Partial source outage -> keep previous cursor, mark degraded source.
- Duplicate daemon claim -> DB lease prevents double-processing.
- Parse failure -> store raw payload and parse error for replay.
- No executor online -> jobs remain queued; freshness SLA depends on at least one healthy executor being online.

### 5.7 Intelligence Pipeline Data Flow

#### Data Flow: Preliminary Qualification

1. Read normalized notice.
2. Determine deadline and expiry horizon.
3. Reject if deadline is within 30 days.
4. If deadline is missing or cannot be normalized confidently, route to manual review rather than passing automatically.
5. Use explicit category fields first:
   - `goods` passes,
   - `services` fails,
   - `works` fails unless the notice clearly describes a separable goods-delivery opportunity,
   - `mixed/unknown` proceeds to AI-assisted classification.
6. Extract product candidates and quantities.

#### Data Flow: Supplier Price Enrichment

1. Generate search profile from contract title, description, CPV, and extracted line items.
2. Query UK/EU sources.
3. Query China-oriented sources.
4. Score comparability.
5. Save quotes with evidence and confidence.

#### Data Flow: Landed Cost

1. Select best supplier quote pairs.
2. Infer commodity code candidates.
3. Query HMRC tariff measures.
4. Select logistics mode by quantity, weight, and volume assumptions.
5. Fetch freight estimates.
6. Convert to GBP using Xe snapshot.
7. Compute both:
   - economic landed cost and net margin on an ex-VAT basis,
   - cash-outlay view including recoverable VAT where relevant.
8. Store warnings and confidence.

### 5.8 Dashboard Data Flow

#### Data Flow: Operator Review

1. User opens dashboard.
2. Dashboard queries canonical procurement processes by state from Supabase.
3. User opens opportunity detail.
4. Detail view loads:
   - canonical process summary,
   - normalized source notices,
   - source links,
   - pricing evidence,
   - logistics/customs assumptions,
   - manifest,
   - agent run history.
5. User chooses:
   - reject,
   - watch,
   - rerun enrichment,
   - start bidding workflow.

### 5.9 Bidding Flow

In many cases the notice source and the submission portal are different. `Find a Tender` and `Contracts Finder` are discovery/publication sources, while the actual bidder interaction often happens on downstream eSourcing portals such as Jaggaer, Atamis, Proactis, PCS-Tender, or authority-specific procurement systems. Bid workflows should therefore be modeled around the **underlying submission portal**, not the notice discovery source.

```text
operator clicks "bid"
  -> create bid job
  -> daemon claims job
  -> portal-specific skill selected
  -> company profile injected into kickoff prompt
  -> browser automation fills downstream portal forms
  -> draft submission or request-for-bid prepared
  -> evidence/screenshot/log artifacts stored
  -> job marked draft_ready, needs_review, or submitted depending on workflow stage
```

### 5.11 Error Handling Strategy

| Error | Code | Handling |
|-------|------|----------|
| Source API unavailable | `SOURCE_UNAVAILABLE` | retry + degrade source status |
| Notice parse failed | `NOTICE_PARSE_FAILED` | store raw payload, mark manual review |
| Goods classification uncertain | `GOODS_CLASSIFICATION_LOW_CONFIDENCE` | keep notice, require review |
| Supplier match weak | `SUPPLIER_MATCH_LOW_CONFIDENCE` | do not auto-qualify |
| Commodity code uncertain | `COMMODITY_CODE_LOW_CONFIDENCE` | route to manual review |
| Freight estimate weak | `LOGISTICS_LOW_CONFIDENCE` | use manual quote/broker escalation |
| Agent workflow failed | `AGENT_RUN_FAILED` | retry if safe; store logs/screenshots |

#### Error Handling Example

```ts
type ConfidenceGate =
  | "pass"
  | "manual_review"
  | "reject";

function resolveConfidenceGate(score: number, floor = 0.7): ConfidenceGate {
  if (score >= floor) return "pass";
  if (score >= 0.45) return "manual_review";
  return "reject";
}
```

## 6. Implementation Considerations

### 6.1 Complexity Analysis

**Overall Complexity:** Very High

**Complexity Breakdown:**

| Component | Complexity | Reason |
|-----------|------------|--------|
| Procurement ingestion | Medium | official APIs help a lot |
| Notice normalization | Medium | OCDS helps, but not all sources are identical |
| Goods qualification | Medium | rules + AI hybrid |
| Product extraction | High | noisy natural language, quantities often ambiguous |
| Supplier price matching | Very High | comparable-product matching is difficult |
| Landed-cost engine | Very High | logistics + customs + FX + assumptions |
| Dashboard | Medium | standard CRUD/search/detail flows |
| Bid automation | Very High | portal-specific, brittle, compliance-sensitive |
| Local daemon orchestration | High | leases, secrets, local execution, logs |

**Risk Areas:**

1. Product matching between contract descriptions and marketplace listings.
2. Commodity-code accuracy and duty/VAT correctness.
3. Freight-mode selection and cost assumptions for large contracts.
4. Duplication/coordination across multiple local clients.
5. Automation brittleness in bid workflows.

### 6.2 Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Wrong product match inflates margin | High | High | confidence scoring + evidence + manual review |
| Incorrect notice-to-process merging conflates separate opportunities | Medium | High | conservative merge heuristics + merge confidence + manual unmerge tooling |
| HS code is wrong | Medium | Critical | candidate-code ranking + ATR workflow + broker escalation |
| Freight estimate too optimistic | High | Critical | mode-aware engine + confidence + manual quote threshold |
| VAT recoverability is modeled incorrectly | Medium | High | store VAT-registration assumptions explicitly and show economic-margin vs cash-outlay views separately |
| Duplicate jobs across local clients | Medium | High | DB leases + heartbeats + idempotent writes |
| No executors online for queued work | Medium | High | hosted scheduler + durable queue + at least one designated always-on executor, with cloud fallback later if needed |
| Portal UI changes break bid workflow | High | Medium | portal-specific skills + screenshots + health checks |
| Marketplace API policy changes | High | Medium | adapter interfaces + source abstraction |
| FX volatility changes decision outcome | High | Medium | stored rate snapshots + recalculation triggers |

### 6.3 Security Considerations

**Authentication:**

- Dashboard users authenticate through Supabase Auth or compatible OIDC.
- Local daemon should use a device-scoped token, scoped database role, or brokered hosted API for privileged job claims.
- Agent CLIs use locally managed credentials, never browser-exposed secrets.

**Authorization:**

- RLS for all user-facing tables.
- Do not distribute the Supabase service-role key to desktop clients.
- Prefer a dedicated `daemon` role exposed through RLS-safe RPCs or a thin hosted broker API for privileged operations.
- Distinct roles:
  - `viewer`
  - `operator`
  - `admin`
  - `daemon`

**Data Protection:**

- Store secrets in desktop OS keychain / Tauri secure storage strategy, not plain-text configs.
- Encrypt especially sensitive company profile fields if stored centrally.
- Redact agent logs before showing them broadly.

**Security Risks:**

| Risk | Mitigation |
|------|------------|
| Prompt injection via source content | strict extraction schemas + sandboxed agent context |
| Secret leakage to agent logs | scoped env vars + redaction + non-browser secret handling |
| Overpowered Tauri shell execution | explicit Tauri plugin permissions and sidecar allowlists |
| Cross-tenant data exposure | RLS + broker/service-tier isolation + organization scoping |
| Unsafe CLI execution | launch via bounded commands, fixed working dirs, strict envs |

### 6.4 Performance Considerations

**Performance Targets:**

- Incremental ingestion per source should finish in minutes, not hours.
- Opportunity detail page should load in under 2 seconds from warm cache.
- Rerunning enrichment for one contract should begin immediately.
- Job queue should remain responsive even when long agent tasks are running.

**Optimization Strategies:**

- Poll sources incrementally with cursors.
- Keep raw payloads and normalized projections separate.
- Use async worker queues for heavy enrichment.
- Cache FX and tariff lookups for short TTL windows.
- Precompute dashboard summary tables/materialized views.

**Potential Bottlenecks:**

| Bottleneck | Mitigation |
|------------|------------|
| Supplier search explosion | limit search permutations, use line-item heuristics |
| Agent runtime saturation on user machine | daemon concurrency caps |
| Large manifest generation | generate async and cache artifacts |
| Dashboard search over large JSON payloads | normalized columns + GIN indexes + FTS |

## 7. Architectural Decisions

### ADR-001: Use Official Procurement APIs Before Scraping

**Status:** Accepted

**Context:**

UK procurement sources already expose structured APIs/OCDS outputs. Generic scraping would add fragility without upside.

**Decision:**

Build API-first connectors for Find a Tender, Contracts Finder, and optionally PCS. Use HTML/browser fallbacks only where no viable API exists.

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| A: API-first connectors | structured, stable, compliant | requires source-by-source implementation |
| B: Generic HTML scraping | quick to start | brittle, poor structure |
| C: Third-party aggregators | less engineering | vendor dependency, reduced control |

**Rationale:**

The official APIs are materially better than scraping and align with open-contracting standards.

**Consequences:**

- Positive: better data quality and incremental sync support.
- Negative: connector implementation must respect each source’s semantics.

**User Input Required:** No

### ADR-002: Use Supabase/Postgres as the Shared Control Plane

**Status:** Accepted

**Context:**

The system needs relational auditability, multi-client coordination, RLS, artifact references, and compatibility with Rust workers.

**Decision:**

Use Supabase/Postgres for the core data plane.

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| A: Supabase/Postgres | strongest fit, mature auth/RLS, SQL power | more explicit architecture work |
| B: Convex | great realtime, easy backend model | weaker fit for SQL-heavy control plane |
| C: SpacetimeDB | exciting realtime model | maturity/fit risks for this workload |

**Rationale:**

This product is a workflow and evidence system more than a realtime shared-state toy. Postgres is the right center.

**Consequences:**

- Positive: auditability, analytics, flexible workers.
- Negative: must design queueing and orchestration explicitly.

**User Input Required:** No

### ADR-003: Use Tauri v2 With a Rust Daemon

**Status:** Accepted

**Context:**

The user wants local background execution and values Rust robustness.

**Decision:**

Use Tauri v2 for desktop shell and a Rust daemon/sidecar for background work.

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| A: Tauri + Rust daemon | lightweight desktop, strong local execution | two-language stack |
| B: Electron + Node daemon | familiar web tooling | heavier runtime |
| C: Pure web app only | simpler deploy | cannot satisfy local execution requirement |

**Rationale:**

Tauri aligns with the desktop-first ops model and Rust is a good fit for process management and deterministic cost logic.

**Consequences:**

- Positive: lighter desktop footprint, strong systems language for daemon.
- Negative: desktop and web frontends should share UI, not runtime assumptions.

**User Input Required:** No

### ADR-004: Do Not Make PTY Emulation the MVP Orchestrator

**Status:** Accepted

**Context:**

Local CLI inspection shows both Codex and Claude support non-interactive modes suitable for daemon execution.

**Decision:**

Launch agent CLIs as child processes in non-interactive mode first. Add PTY support only when proven necessary.

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| A: child process non-interactive | simpler, cleaner logs, easier retries | may miss rare TTY-dependent flows |
| B: PTY-first runtime | flexible for interactive tools | more complexity up front |

**Rationale:**

The CLIs already expose execution-oriented interfaces. A terminal emulator should not be the default architecture.

**Consequences:**

- Positive: cleaner daemon design.
- Negative: some workflows may later require a PTY adapter.

**User Input Required:** No

### ADR-005: Skills Are Workflow Assets, Not the Workflow Engine

**Status:** Accepted

**Context:**

The user wants skill-based architecture. That is good for reusable instructions, but dangerous if skills become the system state.

**Decision:**

Use skills for agent behavior and workflow-specific playbooks, while durable orchestration stays in database-backed job state.

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| A: skills as assets + DB orchestration | reliable and inspectable | more architecture work |
| B: skills as orchestration | fast to prototype | state becomes opaque and fragile |

**Rationale:**

Agent prompts are not a durable job scheduler.

**Consequences:**

- Positive: replayability and observability improve.
- Negative: requires explicit workflow modeling.

**User Input Required:** No

### ADR-006: Build an Internal Landed-Cost Engine

**Status:** Accepted

**Context:**

Third-party shipping/tax APIs are useful, but margin decisions need explainable and auditable numbers.

**Decision:**

Implement customs, valuation, shipping mode selection, and FX combination as internal logic using authoritative and commercial source inputs.

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| A: internal engine + official data | explainable, auditable | more engineering |
| B: third-party black-box estimator | quick | opaque and weaker for high-stakes decisions |

**Rationale:**

The core business value is the decision engine. That cannot be delegated blindly.

**Consequences:**

- Positive: higher trust and better override behavior.
- Negative: implementation complexity is high.

**User Input Required:** No

### ADR-007: Human Review Is Required for Low-Confidence Commercial Decisions

**Status:** Accepted

**Context:**

Some errors are tolerable. Wrong landed cost or wrong portal submission is not.

**Decision:**

Any opportunity with low supplier-match confidence, low commodity-code confidence, or low logistics confidence requires manual review before being promoted or bid.

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| A: confidence-gated human review | safer, more honest | more operator involvement |
| B: full automation | fast | unacceptable error risk |

**Rationale:**

The cost of false positives is high.

**Consequences:**

- Positive: fewer bad bids and fewer margin illusions.
- Negative: lower throughput until models and heuristics mature.

**User Input Required:** No

### ADR-008: Separate Desktop and Web Shells, Share UI and Domain Packages

**Status:** Proposed

**Context:**

The user prefers Tauri + Next.js, but Tauri desktop constraints conflict with SSR-heavy assumptions.

**Decision:**

Prefer separate shells with shared packages:

- `apps/desktop` on Tauri + static frontend,
- `apps/web` for hosted access,
- `packages/ui` for shared interface,
- `packages/contracts-schema` for shared domain models.

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| A: split shells, shared packages | operational clarity, cleaner desktop fit | more repo structure |
| B: single Next app everywhere | less duplication | desktop constraints leak into product architecture |

**Rationale:**

Shared code is good. Shared runtime assumptions are not always good.

**Consequences:**

- Positive: cleaner desktop/web split.
- Negative: some duplicated shell code.

**User Input Required:** Yes

## Appendices

### A. Suggested Margin Logic

#### Gross Margin Gate

Use an ex-VAT revenue basis and supplier cost only:

```text
gross_margin = (contract_revenue_ex_vat - supplier_cost) / contract_revenue_ex_vat
gross_estimate_confidence = confidence_assigned_to_the_pre-landed-cost_estimate

if gross_margin >= 0.30 and gross_estimate_confidence >= confidence_floor:
  qualify_for_landed_cost_stage
else if gross_estimate_confidence < confidence_floor:
  route_to_manual_review
else:
  reject_or_deprioritize
```

#### Net Margin Gate

Use an ex-VAT economic margin view. Do not blindly subtract recoverable import VAT from economic margin if the importing entity is VAT-registered and can reclaim it.

```text
net_margin_economic = (
  contract_revenue_ex_vat
  - supplier_cost
  - freight_cost
  - customs_duty
  - uk_final_mile
  - other_fees
) / contract_revenue_ex_vat

cash_outlay = (
  supplier_cost
  + freight_cost
  + customs_duty
  + uk_final_mile
  + other_fees
  + import_vat_if_not_recoverable_or_if_cashflow_tracking_is_needed
)

if net_margin_economic >= 0.20 and net_estimate_confidence >= confidence_floor:
  final_qualified
else if net_estimate_confidence < confidence_floor:
  manual_review_required
else:
  not_qualified
```

### B. Suggested Confidence Model

Use a weighted confidence score as an initial heuristic only. The weights below are priors for MVP and should be recalibrated against observed operator decisions and realized sourcing outcomes rather than treated as statistically validated probabilities.

```text
final_confidence =
  (0.25 * goods_classification_confidence) +
  (0.25 * product_match_confidence) +
  (0.20 * commodity_code_confidence) +
  (0.20 * freight_confidence) +
  (0.10 * fx_freshness_confidence)
```

Then apply:

- `>= 0.80` -> high confidence
- `0.60 - 0.79` -> usable with review
- `< 0.60` -> manual review required

For implementation, `gross_estimate_confidence` and `net_estimate_confidence` should be stage-specific projections of the same confidence framework. A reasonable initial `confidence_floor` for automated progression is `0.60`, but this should be calibrated against operator outcomes.
