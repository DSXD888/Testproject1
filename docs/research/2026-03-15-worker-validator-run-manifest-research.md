## 1. Executive Summary

### The Problem

The existing architecture validates agent skill output using code-native tools: JSON schema checks (syntactic), hardcoded business invariant rules (semantic), and statistical envelope checks (behavioral/drift). These catch structural errors but miss semantic ones. A skill that navigates to the wrong page, extracts perfectly-structured data from the wrong source, and returns valid JSON will pass all three gates. The output looks correct. The data is completely wrong.

Skills are not code. They are human-readable, step-by-step workflow instructions that an LLM agent follows with judgment. The validation must match the medium: semantic validation requires semantic judgment, which means another agent.

### The Solution

A **worker-validator coupled architecture** where every agent skill run produces two artifacts:

1. **Result contract** — the structured data output (already designed in the main research plan).
2. **Run manifest** — a new MD document the worker agent writes at the end of every run, narrating: what steps were taken, what was found, what decisions were made, what looked wrong, and what evidence supports the results.

After the worker completes, the daemon automatically enqueues a **validator agent job** — a separate agent session that reads the run manifest, the result contract, the skill's expected behavior, and relevant context, then renders a **validation verdict**: approved, rejected, or flagged for human review.

Results only advance in the pipeline after the validator approves. Rejected results are quarantined. Flagged results await operator review.

### Why This Matters

1. **Catches what code cannot.** A validator agent can detect "the agent extracted 5 notices but 3 are from Scotland, not England/Wales" or "prices are in USD but the page was supposedly GBP." No linter or schema check catches this.
2. **Enables iterative skill development.** The dry-run loop becomes: write SKILL.md → run against real source → get manifest → validator explains what went wrong → fix SKILL.md → repeat. This is how skills get built in practice.
3. **Makes skills plug-and-play.** Adding a new source means: create SKILL.md, dry-run until validator approves, promote. No daemon code changes. No schema changes. No recompilation.
4. **Shifts quality assurance from code-time to run-time.** Instead of trying to anticipate every failure mode in validation rules, the validator agent reasons about each run in context.

### Key Recommendations

- **Run manifests are a first-class artifact type**, produced by every worker agent run (success or failure), stored alongside forensic bytes in the artifact store.
- **The validator is a skill itself** — source-aware, versioned, with its own result contract (the validation verdict). It runs in contract mode with a low-cost model.
- **Worker and validator are coupled but independent jobs** — the daemon auto-enqueues the validator after the worker completes, but they are separate sessions with independent observability.
- **Validation policy is configurable per skill and promotion stage** — always-validate during development/promotion, sample-validate in stable production, trigger-validate on anomalies.
- **Dry-run mode** writes all artifacts to a scratch location without committing to pipeline state — the core mechanism for iterative skill development.
- **Manual mode** renders the kickoff prompt for copy-paste into a fresh agent session — zero infrastructure needed for early skill prototyping.
- **The existing Output Quality Gate's semantic/drift checks become inputs to the validator**, not a parallel system. Schema validation remains as a fast pre-filter.

## 2. Intent & Requirements Analysis

### 2.1 Problem Statement

**The Problem:**

Skills are human-readable workflow specifications in natural language. An agent follows them with judgment — navigating websites, making extraction decisions, handling unexpected page states. Traditional code testing tools (linters, JSON schema validators, statistical envelope checks) catch structural issues but are fundamentally blind to semantic ones:

- Did the agent navigate to the right page?
- Did it extract data from the intended source, not a redirect or cached version?
- Are the extracted prices actually in the expected currency?
- Did it skip important results because it misunderstood the skill instructions?
- Did it extract data that looks structurally correct but is semantically garbage?

The current architecture's Output Quality Gate catches some of these via hardcoded semantic rules (e.g., "deadline must be after publication date"). But semantic rules must be anticipated and coded in advance. Novel failure modes — and agent workflows produce novel failure modes constantly — pass through unchecked.

**Why It Matters:**

The platform's intelligence thesis depends on data quality. Wrong procurement notices, wrong product matches, wrong prices propagate through the entire pipeline: qualification, search, pricing, landed cost, margin estimation, operator decisions. A single "schema-valid garbage" run that passes validation can corrupt downstream state for dozens of opportunities.

**Current State:**

The main research plan (§4.10, §5.11, §6.5) defines a comprehensive validation and testing strategy — but one designed for code artifacts, not workflow artifacts. The gap is not in the architecture's sophistication but in its ontological assumption: that validation is a code problem.

### 2.2 Deep Intent Summary

The owner is asking for four connected things:

1. **Run manifests** — a narrative record of what the agent actually did, produced by the agent itself, readable by humans and other agents.
2. **Validator agent** — a second agent that reads the manifest and renders semantic judgment, catching what code cannot.
3. **Iterative development pipeline** — dry-run → manifest → validator feedback → improve SKILL.md → repeat, without touching production state.
4. **Plug-and-play skill architecture** — adding a new skill should be: write it, dry-run it, promote it. No daemon changes, no schema changes, no recompilation.

The deeper insight: **the development workflow for skills IS the testing strategy for skills.** If you can't easily run a skill, see what it did, understand why it failed, and iterate — then the testing strategy doesn't matter because skills will never get good enough to test.

### 2.4 Success Criteria

**Functional Criteria:**

- [ ] Every agent skill run produces a structured run manifest as an artifact.
- [ ] Validator agent can read a run manifest + result contract and produce a validation verdict.
- [ ] Validated results are committed to pipeline state; rejected results are quarantined.
- [ ] Dry-run mode executes the full worker + validator pipeline without committing to `state.db`.
- [ ] Manual mode renders a complete kickoff prompt for copy-paste into a fresh agent session.
- [ ] Validation policy is configurable per skill and per promotion stage.
- [ ] The desktop control panel displays run manifests and validation verdicts.
- [ ] Adding a new skill requires only: create skill directory, dry-run until validator approves, configure source binding. No daemon code changes.

**Non-Functional Criteria:**

- [ ] Validator overhead is < 30 seconds per run (contract mode, low-cost model).
- [ ] Validator cost is < 20% of worker cost on average (driven by sampling policy).
- [ ] Run manifests are < 50 KB per run (structured header + focused narrative).
- [ ] Validation verdicts are stored and queryable for trend analysis.

### 2.6 Non-Goals

- **Replacing the existing schema validation.** Schema checks remain as a fast pre-filter. The validator runs after schema validation passes, not instead of it.
- **Validating every production run forever.** Stable skills with long track records can reduce validation frequency. The goal is confidence, not ceremony.
- **Making the validator infallible.** The validator is an agent that can make mistakes. It's a probabilistic quality gate, not a mathematical proof. Its value is in catching the class of errors that code cannot catch at all.
- **Autonomous skill improvement.** The skill-improver agent is a future concept. For now, the loop is: validator rejects → human reads rejection → human fixes SKILL.md.

### 2.7 Constraints

- Validator must run through the same Agent Adapter and execution infrastructure as workers — no special runtime.
- Validator must not require access to live web sources (it reads artifacts, not pages).
- Validator sessions must be short and cheap (contract mode, low-cost model).
- Run manifests must be producible by the worker agent itself, not by daemon-side code (the agent is the one who knows what it did).
- The architecture must not create circular dependencies (validator validates worker, but nothing validates validator).

### 2.8 Key Ambiguities

| Ambiguity | Why It Matters | Working Assumption |
|-----------|---------------|--------------------|
| Should the validator see raw forensic bytes (Layer 3)? | Full PTY output is huge and expensive to process | No — validator reads the run manifest (agent's summary) + result contract + golden assertions. Forensic bytes are for human debugging only. |
| Should validator rejections auto-retry the worker? | Could enable self-healing but also infinite loops | No — rejection quarantines results and alerts operator. Retry is a human decision. |
| Can validators be generic or must they be source-specific? | Generic is cheaper; source-specific is more accurate | Layered: generic base validator + source-specific overlay. Most skills need only the generic validator. |
| Should dry-run mode use a separate SQLite database? | Simpler isolation but more infrastructure | No — dry-run writes to the same `state.db` but in a `dry_run_` prefixed staging area with automatic cleanup. Or simply write artifacts to a scratch directory and skip DB writes entirely. |
| Should the operator be able to override a validator rejection? | Operators may disagree with the validator | Yes — operator override with reason recorded. The validator is advisory for stable skills, mandatory only for promotion gates. |

## 3. Internal Architecture Analysis

### 3.1 Current Validation Architecture

The main research plan defines a three-layer validation pipeline, all implemented as deterministic daemon-side code:

**Layer 1 — Syntactic Validation (Result Contract Validator component):**
- JSON schema match against `result.schema.json`
- Required fields present, types valid, URLs parse correctly
- Failure: `AGENT_OUTPUT_CONTRACT_INVALID` — job fails, artifacts preserved

**Layer 2 — Semantic Validation (Output Quality Gate):**
- Hardcoded business invariant rules:
  - Deadline after publication date
  - Currency consistent with expected locale
  - Source IDs unique within batch
  - Price/unit normalization plausible
  - Lot value totals reasonable relative to notice total
- Failure: `AGENT_SUSPECT_OUTPUT` — results quarantined, not committed

**Layer 3 — Behavioral/Drift Validation (Output Quality Gate):**
- Statistical envelope checks:
  - Null-rate within historical bounds
  - Duplicate rate within historical bounds
  - Result count not collapsing
  - Page fingerprint hash stable
  - Locator fallback depth not suddenly elevated
- Failure: `AGENT_SUSPECT_OUTPUT` — same quarantine path

**The gap:** All three layers ask "does the output look structurally correct?" None ask "did the agent actually do the right thing?" Schema-valid garbage passes all three.

### 3.2 Current Manifest System

The main plan has two manifest concepts, neither of which is a run manifest:

1. **Opportunity manifests** (`manifests` table, push-owned) — Markdown documents explaining why a procurement opportunity is attractive or unattractive. Business-facing, for operator review. Generated by the `manifest-generation` skill.

2. **Error manifests** (`error_manifests` table, local-only) — Structured failure records created only when jobs fail. Contains: pipeline stage, workflow step, error type/message, error context (full locally, redacted in Supabase), skill path, session ID, markdown artifact path, resolution tracking.

Neither is a **run manifest** — a narrative of what the agent did on every run (success or failure). The error manifest is close but only fires on failures, and its content is daemon-generated (structured metadata), not agent-generated (narrative account).

### 3.3 Current Skill Lifecycle

The 6-stage promotion flow (§4.10):

| Stage | Gate | Current Validation |
|-------|------|-------------------|
| Draft | Dev-only | Manual runs only, not scheduler-eligible |
| Candidate | CI lint + smoke canaries | Metadata present, schemas valid, canary inputs exist |
| Canary | Smoke canaries vs live source | Page fingerprint, auth, one small extraction |
| Shadow | Quality comparison vs stable | Fill-rate, duplicate rate, suspect-output rate, cost |
| Stable | Shadow metrics ≥ stable | Scheduler default |
| Rollback | Any time | Rebind to prior stable |

**The gap in draft stage:** The spec says draft skills support "manual runs only" but never describes:
- How to launch a draft skill from the CLI
- How to see the kickoff prompt that would be composed
- How to dry-run without committing results
- How to get structured feedback on what went wrong

The Minimum Viable Experiment (MVE) section says "all skills run from CLI" and "no daemon, no cron, no desktop UI" — but no CLI tooling or workflow is specified.

### 3.4 Current Testing Strategy

The existing strategy (§6.5) is comprehensive for code-native validation:

| Test Type | What It Catches | What It Misses |
|-----------|----------------|----------------|
| Skill linting (CI) | Missing metadata, invalid schemas, missing files | Whether the skill actually works |
| Live smoke canaries | Page fingerprint changes, auth failures, basic extraction | Whether extracted data is semantically correct |
| Golden live journeys | Invariant violations (min results, required fields) | Novel failure modes not covered by invariants |
| Shadow runs | Regression vs stable version | Both versions producing wrong data consistently |
| Production drift | Statistical anomalies in fill-rate, duplicates, etc. | Semantically wrong data with normal statistics |
| Deterministic replay | Parser/validator regressions | Extraction logic regressions (agent-side) |

**The common thread:** Every test type uses code-based assertions. The validator agent fills the gap — it can reason about whether the agent's narrative account (the run manifest) describes behavior that should produce correct results.

### 3.5 Integration Points

Based on exhaustive codebase analysis, the worker-validator architecture touches these existing components:

**Must Integrate With:**
- `workflow_jobs` table — new `kind: validation`, new `parent_job_id` linking validator to worker

## 4. External Technology Research

### 4.1 LLM-as-Judge Pattern

The worker-validator architecture is an application of the **LLM-as-Judge** pattern, which has become a well-established evaluation methodology as of 2025-2026. In this pattern, a capable LLM assesses the quality of outputs produced by another LLM application by reasoning about outputs against defined criteria.

**Key findings from current research:**

- LLM-as-Judge frameworks demonstrate **over 90% alignment with human judgments** across evaluation types, making them viable as automated quality gates.
- The pattern works best when the judge has **clear evaluation criteria** (not open-ended "is this good?") — which maps directly to skill-specific validation rules.
- **Bias mitigation** is critical: the judge should not see the worker's internal reasoning or self-assessment, only the observable outputs and the run manifest narrative. This prevents anchoring bias.
- **Cost-effective evaluation** is achieved by using a lower-cost model as the judge when the evaluation criteria are well-defined and the input is structured (manifest + result contract, not raw PTY bytes).

**Relevance to this architecture:**

The validator agent IS an LLM-as-Judge. The run manifest is the structured input. The validation verdict is the structured output. The skill's `golden.assertions.yaml` and source-specific validation criteria are the evaluation rubric. This is a direct, well-understood application of a proven pattern.

### 4.2 Worker-Validator Patterns in Distributed Systems

The worker-validator pattern (also called maker-checker, four-eyes principle, or dual-control) is a foundational pattern in financial systems, compliance workflows, and safety-critical automation:

- **Financial services:** Every trade, payment, or settlement has a maker (initiator) and a checker (validator). The checker reviews the maker's work before execution.
- **Aerospace/defense:** Every mission-critical computation runs on redundant systems with independent validation.
- **CI/CD pipelines:** Code review (human validator) before merge. Linters and tests are the code-native pre-filter; human review catches semantic issues.

**Key design principles from these domains:**

1. **Independence:** The validator must not share state with the worker during execution. They are separate sessions.
2. **Asymmetric cost:** The validator is cheaper than the worker (review is cheaper than creation).
3. **Non-recursive:** The validator does not need its own validator. If the validator itself is unreliable, the solution is to fix the validator, not add a meta-validator.
4. **Override capability:** Human operators can override the validator in both directions (approve a rejection, reject an approval).
5. **Audit trail:** Every verdict is recorded with full reasoning for post-hoc analysis.

### 4.3 Agent Evaluation Frameworks (2025-2026)

Current agent evaluation platforms (LangWatch, Langfuse, Evidently AI) implement evaluation pipelines that are structurally similar to the proposed architecture:

- **Trace capture** → analogous to the run manifest + forensic bytes
- **Evaluator LLM** → analogous to the validator agent
- **Scoring rubrics** → analogous to `golden.assertions.yaml` + source-specific criteria
- **Dashboard** → analogous to the desktop control panel's validation view

**Key difference:** These platforms evaluate after the fact (offline evaluation). The proposed architecture evaluates inline (the validator's verdict determines whether results commit to the pipeline). This is more like a CI gate than a monitoring dashboard.

### 4.4 Agentic Workflow Patterns

Research on agentic workflows in 2025-2026 identifies several patterns relevant to the proposed architecture:

- **Validator-Reprompting Loop:** A simulation agent executes a plan, a validator checks transitions, and invalid plans are iteratively refined. Industrial automation contexts using this pattern achieve 100% valid-path success within five reprompts.
- **Self-Review:** Agents review their own performance after each run, learning from errors. However, self-review has known bias issues (agents tend to rate their own work favorably). The proposed architecture avoids this by using a separate validator agent.
- **Phased Deployment:** Successful agentic systems use iterative testing with phased promotion (pilot → limited → full), directly mapping to the draft → candidate → canary → shadow → stable flow.

### 5.3 Run Manifest Specification

The run manifest is an MD document produced by the worker agent as part of its skill execution. It is NOT generated by daemon-side code — the agent is the only entity that knows what it actually did.

#### Generation Mechanism

The mandate to produce a run manifest is embedded in the **kickoff prompt**, not in the skill. This means every skill automatically produces a manifest without modifying SKILL.md files. The kickoff prompt includes a standardized instruction block:

```
At the end of your run, produce a run manifest document. This manifest is a
structured Markdown file that narrates what you did during this session. It must
include:

1. A YAML frontmatter header with structured metadata.
2. A Summary section (2-3 sentences).
3. A Steps Taken section listing each major action with outcome.
```

### 5.4 Validator Agent Architecture

The validator is itself a skill that runs through the standard Agent Adapter. It is not special daemon code — it's an agent session like any other.

#### Validator Execution Model

- **Execution mode:** Contract mode (`headless_contract`). No browser needed.
- **Model profile:** `structured_extract_low_cost`. The validator reads structured input (manifest + result contract) and produces structured output (verdict). This does not require premium reasoning.
- **Duration:** Target < 30 seconds. The validator reads a < 50 KB manifest and a result contract, not raw PTY bytes.
- **Resource allocation:** Low priority in the resource arbiter. Worker jobs always take precedence.

#### Validator Skill Structure

```text
skills/
  validation/
    base/
      SKILL.md                    # Generic validation logic
      result.schema.json          # Validation verdict schema
      checkpoint.schema.json      # (empty — validators don't checkpoint)
      canary.inputs.jsonl          # Sample manifests for smoke testing
      golden.assertions.yaml       # Expected verdict patterns
    procurement-ingestion/
      SKILL.md                    # FTS/CF/PCS-specific validation criteria
    supplier-enrichment/
      SKILL.md                    # eBay/Amazon/Alibaba/1688-specific criteria
    document-acquisition/
      SKILL.md                    # Document download validation criteria
    product-extraction/
      SKILL.md                    # Product extraction validation criteria
    landed-cost/
      SKILL.md                    # Landed cost calculation validation criteria
```

#### Validator Skill Layering

Validators use a **base + overlay** pattern:

1. **Base validator** (`skills/validation/base/SKILL.md`) — checks that apply to ALL skill runs:
   - Run manifest is well-formed and complete
   - Outcome class matches the narrative (doesn't claim "completed" while describing failures)
   - Items processed count matches result contract count
   - No contradictions between manifest sections
   - Warnings are plausible given the narrative
   - Page fingerprint was verified (for browser skills)
   - Locale/currency was verified (for browser skills)
   - Evidence links are present and reference real artifacts

2. **Domain overlay** (e.g., `skills/validation/procurement-ingestion/SKILL.md`) — source-specific checks:
   - Extracted notices are from the expected source (not cross-contaminated)
   - OCIDs have the expected format for this source
   - Deadline dates are in the future (not historical)
   - Buyer names are plausible UK public bodies
   - Currency is GBP (not EUR or USD)
   - Category codes match expected CPV ranges

The daemon loads the base validator + domain overlay into the validator's context. If no domain overlay exists, the base validator runs alone.

#### Validator Inputs

The validator agent receives:

| Input | Source | Purpose |
|-------|--------|---------|
| Run manifest (full text) | Worker's artifact | Primary review document — the agent's own narrative |
| Result contract (full or sampled) | Worker's output | Verify claims in manifest match actual data |
| `golden.assertions.yaml` | Worker skill directory | Expected invariants for this skill |
| OQG semantic signals | Daemon-computed | Code-based semantic check results (deadline-after-publication, etc.) as additional context |
| OQG drift signals | Daemon-computed | Statistical drift metrics (fill-rate, duplicate rate, etc.) as additional context |
| Historical run summary | Daemon-queried | Last N run outcomes for trend context (e.g., "this skill has been failing 3 out of 10 runs lately") |
| Source-specific validation criteria | Domain overlay skill | What "correct" looks like for this source |

**What the validator does NOT receive:**
- Raw forensic bytes (Layer 3) — too large, too noisy
- The worker's internal reasoning or chain-of-thought — prevents anchoring bias
- The SKILL.md itself — the validator judges results, not intentions

### 5.5 Validation Verdict Specification

The validator produces a validation verdict as its result contract:

```json
{
  "verdict_version": "1.0",
  "worker_job_id": "job-abc-123",
  "worker_session_id": "session-xyz-456",
  "verdict": "approved",
  "confidence_bps": 9200,
  "summary": "Run produced 12 valid FTS notices matching expected source, locale, and currency. One minor warning about non-standard deadline format is acknowledged and correctly handled.",
  "issues": [
    {
      "severity": "info",
      "category": "data_quality",
      "description": "One notice (054389) has a heuristically-parsed deadline with reduced confidence. The agent correctly flagged this in the manifest.",
      "evidence": "Manifest §Warnings, notice 2026/S 000-054389",
      "suggestion": "No action needed — correctly handled."
    }
  ],
  "quality_assessment": {
    "manifest_completeness": "complete",
    "narrative_consistency": "consistent",
    "evidence_present": true,
    "fingerprint_verified": true,
    "locale_verified": true,
    "result_count_matches_manifest": true
  },
  "skill_improvement_suggestions": []
}
```

#### Verdict Values

| Verdict | Meaning | Daemon Action |
|---------|---------|--------------|
| `approved` | Run is semantically correct; results should be committed | Commit results to pipeline, advance stage |
| `rejected` | Run has semantic errors; results should not be committed | Quarantine as `AGENT_SUSPECT_OUTPUT`, create error manifest with validator's reasoning, alert operator |
| `flagged` | Run is ambiguous; human review needed | Hold results in `pending_validation_review` state, alert operator, do NOT commit or quarantine |

#### Issue Severity Levels

| Severity | Meaning | Effect on Verdict |
|----------|---------|------------------|
| `critical` | Data integrity risk — wrong source, wrong locale, wrong currency, fabricated data | Forces `rejected` |
| `warning` | Quality concern — reduced confidence, missing fields, unusual patterns | Accumulates; 3+ warnings may force `flagged` |
| `info` | Observation — noted but not a problem | No effect on verdict |

#### Issue Categories

| Category | Examples |
|----------|---------|
| `wrong_source` | Data extracted from wrong website or wrong section |
| `wrong_locale` | Currency/language/country mismatch |
| `data_fabrication` | Manifest describes extraction but result contains data not plausibly from the source |
| `data_quality` | Missing fields, reduced confidence, heuristic parsing |
| `missing_data` | Expected data not extracted (low fill-rate) |
| `semantic_error` | Logical inconsistencies (deadline before publication, negative prices) |
| `suspicious_pattern` | Unusual patterns that suggest extraction problems (all prices identical, all dates same) |
| `manifest_inconsistency` | Manifest narrative contradicts result contract or itself |
| `coverage_gap` | Expected pages/sections not visited per skill instructions |
| `policy_violation` | Skill budget exceeded, unauthorized side effects, non-compliance |

### 5.6 Validation Policy Engine

Not every run needs validation. The policy engine determines when to validate based on configurable rules.

#### Policy Configuration

```yaml
# Example: per-skill validation policy
validation_policy:
  procurement-ingestion/fts:
    draft: always          # Every run validated
    candidate: always      # Every run validated
    canary: always         # Every run validated
    shadow: always         # Every run validated (compare with stable)
    stable: sample         # Sample validation
    sample_rate: 0.1       # Validate 10% of stable runs
    trigger_on:            # Always validate when these conditions are true
      - fill_rate_drop > 0.2       # Fill rate dropped 20%+ vs rolling average
      - duplicate_rate_spike > 0.1 # Duplicate rate spiked 10%+
      - first_run_after_version_change  # Always after skill update
      - suspect_output_in_last_5   # Recent suspect output detected
      - operator_requested         # Operator manually requested validation

  supplier-enrichment/alibaba:
    draft: always
    candidate: always
    canary: always
    shadow: always
    stable: always         # Alibaba scraping is high-risk; always validate
```

#### Policy Decision Flow

```text
Worker job completes with result contract
    │
    ▼
Schema validation passes? ──No──→ AGENT_OUTPUT_CONTRACT_INVALID (no validator needed)
    │
    Yes
    │
    ▼
Validation Policy Engine:
    │
    ├── Stage is draft/candidate/canary/shadow? ──→ ALWAYS VALIDATE
    │
    ├── Stage is stable?
    │   ├── Policy is "always"? ──→ VALIDATE
    │   ├── Policy is "sample"? ──→ Roll dice (sample_rate) ──→ VALIDATE or SKIP
    │   ├── Policy is "trigger"? ──→ Check trigger conditions ──→ VALIDATE or SKIP
    │   └── Policy is "skip"? ──→ SKIP (commit directly)
    │
    ├── Any trigger condition met? ──→ VALIDATE (regardless of sample/skip policy)
    │
    └── Operator manually requested? ──→ VALIDATE

    │
    ▼
VALIDATE: Enqueue validator job, hold results pending verdict
SKIP: Commit results directly (OQG code checks still run)
```

**Important:** When validation is skipped, the existing code-based Output Quality Gate still runs. The validator replaces OQG's semantic judgment, not its existence. Statistical drift checks always run.

### 5.7 Progressive Skill Requirements by Stage

A key enabler of plug-and-play composability: draft skills should NOT require the same files as production skills. Requirements grow as the skill matures through the promotion pipeline.

| Stage | Required Files | Validation Mode | DB Writes |
|-------|---------------|-----------------|-----------|
| **Draft** | `SKILL.md` only | Manual (human reads manifest) or dry-run + validator | None (scratch only) |
| **Candidate** | + `result.schema.json` + `canary.inputs.jsonl` | CI lint + validator on every run | None (scratch only) |
| **Canary** | + `checkpoint.schema.json` + `golden.assertions.yaml` | Validator on every run against live source | Production (small %) |
| **Shadow** | All production files | Validator on every run, shadow comparison | Non-authoritative |
| **Stable** | All production files | Per validation policy (always/sample/trigger) | Authoritative |

**The key principle:** At draft stage, all you need is a `SKILL.md` and the ability to dry-run it. The manifest + validator feedback tells you what's working and what isn't. Production files (`result.schema.json`, `golden.assertions.yaml`, etc.) are created incrementally as the skill matures — often informed by what the validator flagged during dry runs.

This means the barrier to starting a new skill is: one file, one command. Everything else comes later.

### 5.8 Run Manifests as Fourth Observability Layer

The main research plan defines a three-layer observability model. Run manifests introduce a **fourth layer**:

| Layer | Source | Content | Drives State? | Audience |
|-------|--------|---------|--------------|----------|
| **1 — Control** | Daemon | Session lifecycle events (spawn, exit, reap, cleanup verdict) | Yes | Daemon, operator |
| **2 — Protocol** | Adapter | Parsed vendor events (checkpoints, result contract, auth challenges) | Yes | Daemon, operator |
| **3 — Forensic** | Raw capture | Immutable PTY bytes or stdout/stderr | No (debugging only) | Human debugger |
| **4 — Narrative** | Agent (NEW) | Run manifest — agent's own account of what it did, why, and what went wrong | No (validation input) | Validator agent, operator, skill developer |

**Critical rule (extended):** Layers 1 and 2 drive workflow state. Layer 3 is for post-hoc debugging. Layer 4 is the validation input — it informs the validator's semantic judgment, which then influences whether results commit, but the manifest itself never drives state directly.

Layer 4 fills a gap that Layers 1-3 cannot:
- Layer 1 knows the session started and ended, but not what the agent chose to do.
- Layer 2 knows checkpoints were written and data was extracted, but not whether the agent navigated correctly or made sound decisions.
- Layer 3 has every byte of output, but is too large and noisy for automated semantic review.
- **Layer 4 is the agent's purposeful, structured summary — designed for both human and agent consumption.**

### 5.9 Validator Failure Handling

What happens when the validator itself fails?

| Validator Outcome | Cause | Daemon Action |
|-------------------|-------|--------------|
| Valid verdict produced | Normal operation | Process verdict (approve/reject/flag) |
| Validator schema validation fails | Validator produced invalid JSON | Treat as validator error, NOT worker error. Fall back to OQG code checks. If OQG passes, commit with `validation_skipped_validator_error` flag. Alert operator. |
| Validator session crashes/stalls | Agent stalled, API error, timeout | Same fallback: OQG code checks. Commit with `validation_skipped_validator_error` flag. Create error manifest for the validator failure itself. |
| Validator exits with `failed` outcome | Validator skill error | Same fallback. |

**The principle:** A broken validator should never block the pipeline. Workers can operate without validators (they did in the original architecture). The validator is an improvement layer, not a hard dependency. If the validator is unreliable, fix the validator skill — don't let it hold up production.

**Validator health tracking:**
- Track validator success rate as a skill-level metric (same as worker skills)
- If validator fails 3+ times consecutively, auto-disable validation for that domain and alert operator
- Validator errors create their own error manifests (distinct from worker error manifests)

### 5.10 Continuation-Required and Multi-Segment Validation

When a worker exits with `continuation_required`, validation must handle partial results:

**Policy:** Validate each segment independently. Do not wait for all segments to complete.

**Rationale:**
- Segments may take hours or days to all complete.
- Each segment's results are independently committed via checkpoints.
- Waiting for the final segment would block pipeline progress.
- Each segment's run manifest is self-contained (it describes what happened in that segment).

**Flow:**
```
Segment 1: Worker runs → result (partial) + manifest → validator → approved → commit partial
Segment 2: Worker runs (with resume token) → result (partial) + manifest → validator → approved → commit partial
Segment 3: Worker runs → result (final) + manifest → validator → approved → commit final
```

If any segment is rejected, only that segment's results are quarantined. Prior committed segments remain. The daemon does NOT automatically retry rejected segments — the operator decides whether to re-run, fix the skill, or override.

### 5.15 Dry-Run Mode

Dry-run mode executes the full worker + validator pipeline but writes no persistent state to the production database.

#### Mechanics

1. **Scratch workspace:** All artifacts written to `artifacts/scratch/<dry-run-id>/` instead of `artifacts/sessions/YYYY/MM/`.
2. **No DB writes:** Worker results are NOT committed to `state.db`. No outbox entries. No stage head advances. No pipeline assessment updates.
3. **Validator still runs:** The validator reads from the scratch workspace.
4. **Session logs recorded:** `agent_session_logs` entries ARE written (with a `dry_run: true` flag) so that session metrics are captured for telemetry.
5. **Cleanup:** Scratch workspace is retained until the operator explicitly deletes it or a configurable retention period expires (default: 7 days).

#### CLI Interface

```bash
# Dry-run with default inputs
daemon skill dry-run procurement-ingestion/fts

# Dry-run with explicit inputs
daemon skill dry-run supplier-enrichment/alibaba \
  --input '{"query": "A4 paper 80gsm", "source": "alibaba"}'

# Dry-run with specific skill version
daemon skill dry-run procurement-ingestion/fts --version 2026.03.12-4

# Dry-run without validator (just worker + manifest)
daemon skill dry-run procurement-ingestion/fts --skip-validation

# List recent dry runs
daemon skill dry-runs --list

# View dry-run manifest
daemon skill dry-runs <dry-run-id> --manifest

# View dry-run verdict
daemon skill dry-runs <dry-run-id> --verdict
```

### 5.18 Manifest Truthfulness and Cross-Verification

The most fundamental risk in this architecture: the worker agent writes its own manifest. If the agent navigates to the wrong page but describes the right page in its manifest, the validator may approve garbage.

This is NOT a theoretical concern. LLM agents can confabulate — especially when instructed to produce a narrative. The manifest is the agent's self-report, not an objective record.

#### Mitigation Strategy (Defense in Depth)

**1. Cross-check manifest claims against result contract (validator responsibility):**
- Manifest says "12 items extracted" → result contract should contain exactly 12.
- Manifest says "source URL: find-tender.service.gov.uk" → result contract items should have evidence URLs from that domain.
- Manifest says "currency: GBP" → all prices in result contract should be in GBP.
- Manifest says "no warnings" → result contract should not contain reduced-confidence items.

This is the validator's primary defense: the manifest is a narrative, but the result contract is data. When they disagree, the data wins.

**2. Daemon-generated metadata supplements agent narrative (daemon responsibility):**
The daemon independently records facts that the agent cannot fabricate:
- Session duration (from Layer 1 control events)
- Bytes captured (from forensic artifact)
- Checkpoint count and timing (from Layer 2 protocol events)
- Exit code and cleanup verdict

The daemon attaches these to the validation context. If the manifest says "completed in 30 seconds" but the session lasted 5 minutes, the validator can detect the inconsistency.

**3. OQG statistical checks as independent signal (daemon responsibility):**
Even when the validator approves, the OQG drift checks still run. If the validator approves but fill-rate dropped 50% vs historical, the daemon flags a warning. This catches cases where both the manifest and the validator miss a subtle degradation.

**4. Page fingerprint verification is daemon-verifiable (for browser skills):**
The agent reports `page_fingerprint_matched: true` in the manifest, but the daemon independently records the fingerprint hash from the adapter's page-state events. A mismatch between reported and observed fingerprint is a critical signal.

**5. Result sampling by validator:**
The validator doesn't blindly trust the manifest. For every validation, it samples actual result contract items and spot-checks them against the manifest's narrative. If the manifest describes "extracted UK procurement notices" but sampled items contain Chinese marketplace listings, the narrative is irrelevant.

**Net effect:** The manifest is the primary validation input but NOT the sole signal. The validator cross-checks against the result contract, the daemon provides independent metadata, OQG provides statistical baselines, and the validator samples actual data. All four must be consistent for approval.

### 5.19 Skill-Improver Agent (Architectural Preview)

While implementation is deferred, the skill-improver agent is architecturally important because it completes the autonomous feedback loop. Understanding its shape now ensures the worker-validator architecture doesn't accidentally preclude it.

#### Concept

The skill-improver is a **third agent role** in the skill lifecycle:

```text
Worker → Run Manifest → Validator → Rejection → Skill-Improver → Updated SKILL.md
                                                        ↓
                                                   Dry-run with updated skill
                                                        ↓
                                                   Validator approves?
                                                   Yes → Promote to candidate
                                                   No  → Another improvement cycle
```

#### Inputs

| Input | Source | Purpose |
|-------|--------|---------|
| Current SKILL.md | Skill directory | What the agent was told to do |
| Validator's rejection verdict | `validation_verdicts` table | What went wrong semantically |
| Run manifest | Worker's artifact | What the agent actually did |
| Historical rejection patterns | `validation_verdicts` (last N for this skill) | Recurring failure modes |
| Source-specific context | Domain overlay | What "correct" looks like |

#### Output

A **skill improvement report** containing:
- Root cause analysis (why the skill failed)
- Proposed SKILL.md diff (specific changes)
- Confidence in the proposed fix
- Whether the fix requires human review or can be auto-applied in dry-run

#### Architectural Constraints (set now, even if deferred)

1. **The skill-improver does NOT auto-apply changes to production skills.** It proposes changes that the operator reviews, or at most auto-applies to a draft/candidate copy for dry-run testing.
2. **The skill-improver is itself a skill** — versioned, with its own result contract, running through the standard adapter.
3. **The skill-improver runs in contract mode** with a high-reasoning model profile (`ambiguous_match_high_reasoning`) because understanding why a workflow failed requires strong reasoning.
4. **The daemon auto-enqueues skill-improver jobs only on repeated validator rejections** (e.g., 2+ consecutive rejections for the same skill). Single rejections are operator-handled.
5. **The skill-improver's output is stored as an artifact**, not directly applied. The operator decides whether to apply the diff.

#### Why This Matters Now

The worker-validator architecture must store enough context to enable the skill-improver later:
- Validation verdicts must include `skill_improvement_suggestions` (already specified in §5.5).
- Run manifests must include enough detail about navigation steps and decisions for the improver to reason about what went wrong.
- Historical verdicts must be queryable per-skill for pattern detection.

All of these are already in the current design. The skill-improver is architecturally enabled without additional changes.

### 5.20 Integration with Existing Components

#### Integration: Job Runner

**Current behavior:** Worker job completes → schema validation → OQG checks → commit or quarantine.

**New behavior:** Worker job completes → schema validation → consult validation policy → if validation required: enqueue validator job, hold results → validator completes → process verdict → commit/quarantine/hold.

**When validation is skipped:** OQG statistical drift checks still run (they're cheap and deterministic). Only the semantic judgment moves to the validator.

#### Integration: Outcome Classes

The 6 existing outcome classes remain unchanged. The validator verdict maps into them:

| Validator Verdict | Maps To | Existing Daemon Action |
|-------------------|---------|----------------------|
| `approved` | Worker's original outcome class preserved | Normal commit |
| `rejected` | `suspect_output` | Quarantine, error manifest, alert |
| `flagged` | New hold state: `pending_validation_review` | Hold, alert operator |

The `pending_validation_review` state is a new state between "worker completed" and "results committed." It requires the operator to review and decide.

#### Integration: Error Manifests

When the validator rejects a run, the daemon creates an error manifest exactly as it would for any other `AGENT_SUSPECT_OUTPUT`:

- `error_type`: `VALIDATION_REJECTED`
- `error_message`: Validator's summary
- `error_context`: Full verdict JSON (locally), redacted (Supabase)
- `skill_path`: Worker skill path
- `agent_session_id`: Worker session ID
- `markdown_path`: Points to a generated markdown combining the run manifest + validator verdict for easy operator review

#### Integration: Promotion Flow

The validator integrates into the promotion flow as a gate:

| Stage Transition | Validation Requirement |
|-----------------|----------------------|
| Draft → Candidate | At least 3 consecutive dry-run approvals |
| Candidate → Canary | All smoke canary runs approved by validator |
| Canary → Shadow | All canary runs approved |
| Shadow → Stable | All shadow runs approved + shadow metrics ≥ stable |
| Stable → Rollback | Automatic if 3 consecutive rejections |

#### Integration: Desktop Control Panel

New views:

1. **Run Manifest Viewer** — Read the full manifest for any session. Linked from the session detail page.
2. **Validation Verdict Panel** — See the verdict, issues, confidence, and suggestions. Linked from the job detail page.
3. **Validation Trend Dashboard** — Approval/rejection/flag rates per skill over time. Part of the skill health view.
4. **Dry-Run Launcher** — Trigger a dry-run from the desktop UI. See manifest + verdict in the UI.

## 6. Implementation Considerations

### 6.1 Complexity Analysis

| Component | Complexity | Rationale |
|-----------|-----------|-----------|
| Run manifest generation | Low | It's a kickoff prompt instruction, not code. The agent produces it. |
| Validation orchestrator | Medium | Job enqueue logic, policy lookup, verdict processing. Well-defined state machine. |
| Validation policy engine | Low-Medium | Configuration-driven, simple decision tree. |
| Validator skills (base) | Medium | Requires careful prompt engineering for reliable semantic judgment. |
| Validator skills (domain) | Medium per domain | Source-specific knowledge needed. Can be built incrementally. |
| Dry-run mode | Medium | Scratch workspace management, artifact routing, cleanup. |
| Kickoff prompt renderer | Low | Template composition, straightforward. |
| Database changes | Low | 2 new tables, 2 field additions to existing tables. |
| Desktop UI additions | Medium | Manifest viewer, verdict panel, trend dashboard. |

**Overall:** Medium-High. The architecture is well-defined but requires careful implementation of the validator skills and the orchestration state machine.

### 6.2 Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Validator produces unreliable verdicts | Medium | High | Start with conservative verdicts (flag rather than reject when uncertain). Tune validator skill over time. Track validator accuracy vs human judgment. |
| Run manifest quality varies by agent model | Medium | Medium | Standardize manifest format in kickoff prompt. Validate manifest structure before passing to validator. |
| Validator cost exceeds budget | Medium | Medium | Validation policy engine controls when to validate. Contract mode + low-cost model keeps per-validation cost low. |
| Validator creates false sense of security | Low | High | Document clearly that the validator is probabilistic, not infallible. Maintain code-based drift checks as defense in depth. |
| Circular validation dependency | Low | Low | Explicitly: validators do not have validators. If the validator is unreliable, fix the validator skill. |
| Dry-run scratch accumulates disk space | Medium | Low | Configurable retention period with automatic cleanup. |
| Workers produce low-quality manifests | Medium | Medium | Iterate on the manifest instruction block in the kickoff prompt. The manifest format is standardized and enforceable. |
| Validator rejects correct results (false positive) | Medium | Medium | Operator override capability. Track false positive rate. Tune validator if rate is too high. |
| Worker confabulates in run manifest | Medium | High | Cross-verify manifest claims against result contract data. Daemon provides independent session metadata. OQG drift checks as independent signal. See §5.18. |
| Validator itself crashes or stalls | Low-Medium | Medium | Automatic fallback to OQG code checks. Validator health tracking with auto-disable on repeated failures. See §5.9. |
| Multi-segment jobs with partial rejections | Low | Medium | Validate each segment independently. Rejected segment quarantined; prior committed segments preserved. See §5.10. |

### 6.3 Cost Analysis

**Per-run validator cost estimate:**

| Factor | Value | Rationale |
|--------|-------|-----------|
| Input tokens | ~10,000-15,000 | Run manifest (~5K) + result sample (~3K) + golden assertions (~1K) + OQG signals (~500) + historical summary (~500) + validator skill (~2K) |
| Output tokens | ~500-1,000 | Validation verdict JSON |
| Model | Low-cost tier | `structured_extract_low_cost` profile |
| Estimated cost | ~$0.01-0.03 per validation | At 2026 pricing for low-cost models |
| Duration | ~15-30 seconds | Contract mode, no browser |

**Total validation overhead by policy:**

| Policy | Validation Rate | Cost Multiplier | Use Case |
|--------|----------------|-----------------|----------|
| Always | 100% | ~5-15% of worker cost | Draft, candidate, canary, shadow, high-risk stable |
| Sample 10% | 10% | ~0.5-1.5% of worker cost | Low-risk stable skills |
| Sample 5% | 5% | ~0.25-0.75% of worker cost | Very stable, long track record |
| Trigger-only | ~1-5% | ~0.05-0.75% of worker cost | Proven skills, validate on anomaly |

**Conclusion:** Validation cost is manageable. Even "always validate" adds only 5-15% overhead because the validator is much cheaper than the worker (contract mode, low-cost model, no browser, < 30 seconds).

### 6.4 Testing Strategy for the Validator

**The validator itself needs testing, but NOT another validator.**

| Test Type | What It Covers |
|-----------|---------------|
| **Golden verdict tests** | Feed known-good and known-bad manifests to the validator. Verify it produces correct verdicts. These are deterministic replay tests. |
| **Calibration tests** | Compare validator verdicts against human judgments on a curated set of manifests. Track agreement rate. |
| **False positive monitoring** | Track how often operators override "rejected" verdicts. High override rate → validator is too strict. |
| **False negative monitoring** | Periodically have humans review "approved" runs. If humans disagree → validator is too lenient. |
| **Regression tests** | When the validator skill is updated, replay historical manifests and verify verdicts don't regress. |

### 6.5 Performance Considerations

- **Validation latency adds to job completion time.** For daily cron jobs this is negligible (30 seconds on top of a 5-minute worker run). For manual triggers, the operator sees the result + verdict within a minute.
- **Validator jobs share the resource arbiter.** They are low-priority — if worker jobs need resources, validator jobs wait.
- **Dry-run scratch uses disk space.** Default retention of 7 days with automatic cleanup. Operator can extend or delete manually.
- **Run manifest generation adds ~10-20 seconds to worker runs** (the agent writes the manifest at the end of its session). This is acceptable given the value.

## 7. Architectural Decisions

### ADR-WV-001: Run Manifests Are Agent-Generated, Not Daemon-Generated

**Decision:** The worker agent produces the run manifest as part of its execution, instructed by the kickoff prompt. The daemon does not generate the manifest from session metadata or forensic bytes.

**Rationale:** Only the agent knows what it actually did — what decisions it made, why it skipped items, what looked wrong. Daemon-generated manifests can only report structural metadata (items processed, duration, exit code). The narrative account — the most valuable part — can only come from the agent.

**Consequences:**
- Manifest quality depends on the agent model and the kickoff prompt instructions.
- If the agent fails to produce a manifest (crash, stall), the daemon creates a minimal stub manifest from session metadata.
- The manifest format must be standardized and enforceable via the kickoff prompt.

### ADR-WV-002: Validators Are Skills, Not Daemon Code

**Decision:** Validators are implemented as skills (SKILL.md + result.schema.json) that run through the standard Agent Adapter, not as hardcoded daemon logic.

**Rationale:**
- Validators benefit from the same versioning, promotion, and testing infrastructure as worker skills.
- Source-specific validation criteria can be iterated independently of daemon releases.
- The base + overlay pattern enables progressive specialization without code changes.
- Using the standard adapter means no new runtime infrastructure.

**Consequences:**
- Validator reliability depends on the validator skill quality, which must itself be tested (via golden verdict tests and calibration).
- Validator runs consume agent resources (slots, cost), though at low cost (contract mode).
- Adding validation for a new domain means writing a new validator skill, not modifying daemon code.

### ADR-WV-003: Schema Validation Remains As Fast Pre-Filter

**Decision:** The existing Result Contract Validator (JSON schema check) runs BEFORE the validator agent. If schema validation fails, no validator agent runs — the job fails immediately with `AGENT_OUTPUT_CONTRACT_INVALID`.

**Rationale:** Schema validation is instantaneous and deterministic. It catches structural errors that don't need semantic judgment. Running the validator agent on schema-invalid output wastes time and money.

**Consequences:**
- The validator agent can assume its inputs are schema-valid.
- Two failure paths exist: schema failure (code, instant) and semantic failure (agent, ~30 seconds).

### ADR-WV-004: Validation Policy Is Per-Skill, Not Global

**Decision:** Each skill has its own validation policy (always/sample/trigger/skip) configured per promotion stage. There is no single global "validate everything" or "validate nothing" switch.

**Rationale:** Different skills have different risk profiles. Procurement ingestion from a stable government API is lower risk than supplier scraping from a frequently-changing marketplace. Applying the same validation intensity to both wastes resources on the low-risk skill and under-validates the high-risk one.

**Consequences:**
- Policy configuration must be maintained per skill (but defaults are sane: always for draft-shadow, sample for stable).
- The daemon must look up the policy for each skill at job completion time.

### ADR-WV-005: Validator Does Not See Raw Forensic Bytes

**Decision:** The validator receives the run manifest (agent's summary), the result contract, golden assertions, OQG signals, and historical context. It does NOT receive raw PTY bytes or full forensic session output.

**Rationale:**
- Forensic bytes are 1-256 MB per session. Processing them would make the validator slow and expensive.
- The run manifest is the agent's own summary of the forensic bytes — it's a purpose-built validation input.
- Raw bytes are for human debugging, not for agent validation.

**Consequences:**
- The validator's judgment is based on the agent's self-report (manifest) + the actual results (contract). If the agent lies in its manifest, the validator may be fooled.
- Mitigation: the validator cross-checks manifest claims against the result contract (e.g., "manifest says 12 items extracted" should match result contract length).

### ADR-WV-006: Worker-Validator Is a Coupled Pair, Not Optional Layering

**Decision:** The worker and validator are architecturally coupled — every worker skill has a corresponding validation path, and the daemon treats them as a paired execution model. The validator is not an "optional add-on" that can be removed without architectural consequence.

**Rationale:** The user's core insight is that skills are human-readable workflows, not code. Code-native validation (linters, schema checks) is necessary but insufficient. The validator is the semantic quality gate that makes the entire skill pipeline trustworthy. Without it, the promotion flow (draft → stable) lacks a mechanism to catch the most dangerous failure class: schema-valid semantic garbage.

Making the validator optional at the architectural level (rather than at the policy level) would mean:
- The promotion flow gates would revert to code-only checks, which miss semantic errors.
- New skills would lack a structured feedback mechanism for iterative development.
- The "dry-run → manifest → feedback → iterate" loop would be incomplete.

**Consequences:**
- Every new skill domain should eventually have a validator overlay (generic base validator covers initial needs).
- Validation cost is a permanent operational expense (managed via policy engine, not elimination).
- The daemon's job completion state machine has two paths (validated vs validation-skipped) but both are first-class.

### ADR-WV-007: Run Manifests Are Universal Across All Agent Skill Types

**Decision:** All agent skill runs produce run manifests — browser skills, extraction skills, classification skills, manifest-generation skills, auth-refresh skills, bid-portal skills. The manifest format adapts (browser fields are optional) but the narrative structure is universal.

**Rationale:** The validator's value is not limited to browser scraping. A product-extraction skill that classifies a services contract as goods is a semantic error that no schema check catches. An auth-refresh skill that reports success but didn't actually refresh the session is a semantic error. A manifest-generation skill that produces a narrative about the wrong contract is a semantic error. All of these are caught by a validator reading the run manifest.

**Consequences:**
- The manifest frontmatter schema has required and optional fields (browser fields are optional for non-browser skills).
- Validator domain overlays are needed for each major skill category, not just browser scraping.
- The kickoff prompt's manifest instruction block is included for ALL skills, regardless of type.

## 10. Open Questions

| Question | Impact | Options |
|----------|--------|---------|
| Should the validator see the worker's SKILL.md? | Affects validator's ability to check "did the agent follow instructions" | **Option A:** No — validator judges results, not compliance with instructions. **Option B:** Yes — validator can check if the agent deviated from its playbook. **Leaning:** Option A for base validator, Option B as optional domain overlay capability. |
| Should validator rejections count toward source circuit breaker? | Affects source health management | **Leaning:** No — validator rejections are about data quality, not source availability. Source circuit breaker should trigger only on access/auth errors. |
| Should run manifests be synced to Supabase? | Affects viewing portal capability | **Leaning:** No — manifests are development/debugging artifacts, not viewer-facing. Only the verdict summary is synced. |
| What is the minimum manifest for a crashed/stalled session? | Affects manifest completeness guarantee | **Leaning:** Daemon generates a stub manifest from session metadata (started_at, duration, exit code, last checkpoint, error type) when the agent fails to produce one. |
| Should the skill-improver agent be part of this architecture or separate? | Affects scope and complexity | **Resolved:** Separate. Architecturally previewed in §5.19 but implementation deferred. Worker-validator architecture stores all context the improver will need. |
| How are validator skills themselves promoted? | Validators need quality assurance too | **Leaning:** Golden verdict tests (curated known-good and known-bad manifests) + human calibration checks. Validators don't need their own validators — they're tested against labeled data. |
| Should non-browser skills (product extraction, manifest generation) produce manifests? | Affects scope of manifest system | **Leaning:** Yes — all skill-based agent runs produce manifests. Non-browser manifests omit browser-specific frontmatter (pages_visited, fingerprint, locale) but retain the narrative structure. The validator is equally valuable for catching errors in product extraction ("classified a service contract as goods") as in browser scraping. |
| Should deterministic daemon-side processing (qualification rules, relation resolution) produce manifests? | Affects manifest system scope | **Resolved:** No. Manifests are for agent-executed skills, not deterministic code. Deterministic processing is tested via unit tests and code-based assertions. |
