## 1. Executive Summary

### Feature Overview

Today the pipeline filters **aggressively for pure supply-of-goods**. Two independent code gates reject anything that smells of installation, maintenance, works, or services. That narrowness is starving the bid funnel — there simply aren't enough pure-supply commodity tenders for Sorellon to bid on.

This feature does two coupled things:

1. **Widen the filter** so the pipeline also surfaces **goods-LED contracts that include installation and/or maintenance** (supply-and-fit, supply-install-and-maintain), while **continuing to reject service-only contracts**. Acceptance is decided by a **goods value-share rule**: a contract is in-scope only if the estimated goods cost is ≥ a configurable share (default ~55–60%) of the estimated total (goods + UK non-goods cost: labour + permits/traffic-management).
2. **Build a modular UK installation/maintenance labour-cost engine** that estimates the local UK labour + access-equipment cost of fulfilling such a contract, as a first-class peer to freight/customs/VAT in the existing landed-cost rollup. This lets the goods-share rule actually be computed, and gives the operator a rough "does this even make commercial sense?" triage number before committing real bid effort.

These are **rough, screening-grade estimates** for triage only — not the final bid. They answer "is this worth a closer look / manual input / bid?" and nothing more.

### Key Recommendations

- **Filtering approach:** Make qualification **two-phase** — a Phase-1 *provisional-admit* branch in `determineQualificationDecision` (early), plus a Phase-2 *cost-based goods-value-share dominance gate* after landed cost (the **cost-based** share can't exist at the early stage — see §3.2; a **contract-value** share *can*, and the codebase already computes one — see below) — and relax the description-text service gate (`isServiceDescription`) so it distinguishes *goods-led* from *pure-service*. **No hardcoded category allowlist exists in code today** — the L0 whitelist is documentary — so broadening categories is a gold-set + docs change, not a code rewrite.
- **Reuse the existing early goods-share basis.** `qualifyGoodsOpportunity` / `computeAddressableValue` already derive an `addressableValuePence` (contract-value goods portion) at qualification time. Where the tender itemises goods vs labour/works, this **contract-value** basis is the *preferred* dominance signal and is available at **Phase 1** — the new Phase-2 cost proxy is the fallback for un-itemised tenders (see §3.2, §5.5, ADR-001).
- **Cost engine:** Implement labour estimation as a **new landed-cost skill** (`landed-cost/uk-installation-labour-estimate`), **loaded as a transient skill artifact via `load_skill(...)` and invoked sequentially inside `run_landed_cost_live_loop` exactly like the existing freight/customs/FX skills** — which are **not** registered in `sources/registry.rs` (that registry holds only procurement/marketplace sources; see §3.6 + ADR-002). It feeds the landed-cost rollup via **new explicit labour fields** (with the already-allocated-but-unused `uk_final_mile_cost_gbp_pence` as a zero-migration fallback — see ADR-003). Surgical `main.rs` edits; maximum reuse.
- **Labour data:** A **curated regional rate table** (trade × region × tier), seeded from convergent free sources and refreshed quarterly via an optional enrichment skill. Do **not** live-scrape per estimate. Model region as a multiplier on a national baseline.
- **Goods-share rule:** Make the threshold a **config value** (a strategy / qualification-config constant — it gates at decision synthesis, not on a landed-cost source), not a magic number — this is the operator's primary new strategy knob.

### Critical Decisions Required (resolved with operator in this session)

1. ✅ **Goods-category breadth** → "Broaden cautiously (low-reg only)": add festive/LED lighting, signage, fencing, playground/outdoor, blinds, shelving/racking + install on existing furniture/PPE. Stay clear of biocidal/medical/chemical.
2. ✅ **In-scope rule** → "Goods value-share threshold" (configurable, default 55–60%).
3. ✅ **Labour scope** → "Both one-off install/de-install AND recurring multi-year maintenance."

### Estimated Complexity

**Medium-High.** The cost engine is a clean skill addition (proven pattern). The filtering change is small but *behaviorally* high-risk (it changes what the platform bids on) and demands a strong gold-set + scenario validation suite. The recurring-maintenance modeling and the goods/labour value-split are the genuinely novel modeling pieces.

## 2. Intent & Requirements Analysis

### 2.1 Problem Statement

**The Problem:** The pipeline's filtering is too aggressive. It only passes pure goods-supply contracts, so the funnel of bid-worthy opportunities is too thin for Sorellon to operate against. Meanwhile a large slice of public-sector goods spend is procured as **supply-and-install** or **supply-and-maintain** (furniture fit-outs, shelving/racking installs, signage, fencing, playground equipment, seasonal/festive lighting). The platform currently throws all of those away.

**Why It Matters:** Without expanding, there is no viable bid cadence. But naive expansion is dangerous in two ways: (a) it could let *service-only* contracts in (which Sorellon cannot fulfil and which carry heavy labour/employment exposure), and (b) it breaks the cost model — a supply-and-install contract's economics depend on **UK local labour cost**, which the pipeline currently does not estimate at all. A contract can be margin-positive on goods alone and margin-*negative* once an electrician + cherry-picker are priced in. Surfacing such a contract as "qualified" without the labour line is actively misleading.

**Current State:**
- Filtering rejects mixed/works/services at two gates (see §3.2, §3.3).
- The landed-cost engine models goods + freight + duty + import VAT + FX only (see §3.4). There is no labour dimension.
- The agreed year-1 catalogue (from the 2026-05 session) is the L0 whitelist: office supplies, (non-chemical) cleaning, basic PPE Cat I/II, hand tools, basic wooden furniture, packaging. Biocidal/medical/chemical/bespoke were deliberately excluded to keep pre-bid regulatory load low.

### 2.2 User Stories

```gherkin
As the operator (Sorellon),
I want the pipeline to also surface goods-led contracts that include installation/maintenance,
So that I have enough bid-worthy opportunities to operate a real bid cadence.

As the operator,
I want any such contract to come with a rough UK labour + equipment cost estimate folded into landed cost,
So that I can see at a glance whether the contract is even plausibly profitable before investing bid effort.

As the operator,
I want service-only contracts to STILL be rejected automatically,
So that I never waste time on (or accidentally bid) work Sorellon cannot fulfil.

As the operator,
I want to tune the goods-vs-labour acceptance threshold without a code change,
So that I can make the pipeline more or less aggressive as my appetite changes (the modularity I designed for).
```

**Secondary stories:**
- As the operator, I want the labour breakdown (trade, hours, region, equipment) visible in the desktop control panel and run manifest, so a flagged contract is easy to sanity-check manually.
- As a future maintainer, I want to add a new install-typical goods category by adding gold-set cases + a rate-table row, not by editing daemon logic.

### 2.3 Success Criteria

**Functional:**
- [ ] A "supply and installation of steel shelving" notice is classified **goods-led mixed** and reaches `pass`/`review` (not auto-`reject`), provided estimated goods value-share ≥ threshold.
- [ ] A "grounds maintenance services" (labour-only) notice is **still rejected** (negative control).
- [ ] A pure "supply of A4 copier paper" notice **still passes unchanged** (regression control).
- [ ] For an in-scope install contract, the landed-cost estimate includes a non-zero `installation_labour` component with a 3-point (low/base/high) band and a confidence in bps.
- [ ] The goods value-share threshold is read from config (a strategy / qualification-config constant), not hardcoded.
- [ ] Region is derived from the contract's delivery location and changes the labour estimate accordingly.
- [ ] Recurring maintenance contracts produce a multi-period labour estimate (per-visit × visits/yr × term), not a single one-off number.

**Non-Functional:**
- [ ] Estimate is **screening-grade**: explicitly ±20% tolerance, ex-VAT/labour-only flags carried, never presented as a firm quote.
- [ ] Labour skill failures are **fail-soft** — they degrade the estimate's confidence and route to review, they do not crash the pipeline (mirror freight skill's `blocked` handling).
- [ ] Adding a new region or rate quarter is a JSON edit + version bump, no recompile.

### 2.4 Scope Definition

**MVP (Must Have):**
- Two-phase qualification: Phase-1 provisional-admit branch in `determineQualificationDecision` + Phase-2 goods-value-share dominance gate after landed cost; relaxation of the `isServiceDescription` gate.
- Goods value-share computation (goods landed cost vs goods + non-goods cost: labour + permits) and the configurable threshold gate.
- `uk-installation-labour-estimate` skill producing a 3-point labour estimate keyed off region + installation scope + goods category.
- Curated regional rate table (seed) + access-equipment band table.
- Integration into the landed-cost rollup via new explicit labour fields (ADR-003; `uk_final_mile_cost_gbp_pence` kept as fallback).
- One-off install + de-install modeling (covers the seasonal/festive case).
- Gold-set scenario corpus + E2E validation (Appendix A).
- Desktop/manifest surfacing of the labour line.
- Permits & traffic-management cost component (banded ranges) + `permit_responsibility` flag (Component A3) — basic banded model only.
- Lightweight **no-list/bespoke flag** (no-list CPV / bespoke keyword → route to review with an exclusion reason) — required because the L0 no-list is not code-enforced today (§3.8) and goods-dominant bespoke/no-list items would otherwise pass the dominance gate.

**Phase 2 (Should Have):**
- Recurring/scheduled maintenance modeling (per-visit × frequency × term) as first-class.
- Access-equipment auto-selection (height/site heuristics → MEWP class).
- Quarterly rate-refresh enrichment skill (`source-health`-style canary that re-seeds the table).
- Validation overlay (`overlay-labour-cost`) for semantic sanity of labour estimates.

**Future (Could Have):**
- Live per-estimate enrichment lane for high-value bids (operator-triggered).
- Sub-contractor quote ingestion (treat a UK installer quote like a supplier quote with `quote_class = installer_quote`).
- **Detailed per-authority / per-zone** permit & lane-rental sub-model (MVP ships only banded ranges + the responsibility flag).

### 2.5 Non-Goals & Exclusions

**Explicitly out of scope:**
- **Service-only contracts.** Goods must dominate; no pure labour/consultancy/managed-service bids.
- **Heavily-regulated goods** (biocidal, medical devices, pharma, chemicals, bespoke) — unchanged from the 2026-05 decision. Festive lighting and signage are electrical/low-reg; they do **not** reopen BPR/MHRA.
- **Final/firm pricing.** This engine produces triage estimates only.
- **Doing the installation.** Sorellon subcontracts labour; the platform estimates the *cost* of that subcontract, it does not manage delivery, CDM compliance, IPAF tickets, or working-at-height — those are the subcontractor's burden and a post-win concern (see §6.3).

**Deferred:** BCIS/SPON's licensed authoritative rate feeds (expensive; cite methodology only).

## 3. Internal Codebase Analysis

### 3.1 Architecture Overview

**Project Type:** Monorepo. Rust daemon (`crates/daemon/`, `main.rs` ~1.1 MB) is the orchestration core; TypeScript packages (`packages/{intelligence,bidding,contracts-schema,ui,manifests}`) hold pipeline logic and schemas; agent **skills** (`skills/`) are the modular execution units bound to data sources by a registry; `apps/{desktop,web}` are the Tauri control panel + web viewer. Authority-matrix data layer: local SQLite (operational) + Supabase/Postgres (shared).

**Pipeline shape (deterministic stages, `crates/daemon/src/main.rs` `run_deterministic_pipeline()`):**
`extract_lots → prequalify → qualify_lot → reclassify_candidates → score_quoteability → gross_margin_gate → relate`, with the **landed-cost ("Stage 11") skill jobs** (freight, customs, FX, sizing) driven separately via the job runner, then a decision-synthesis step that assembles the final `LandedCostEstimate`.

The whole thing was designed to be **config-driven and modular** (see the companion infra research): category strategy lives in data/gold-set not code, search strategy lives in input JSON, skills are swappable via registry bindings + promotion stages, and validation is composed via overlays. This feature must honour that — every new piece is a skill, an overlay, a config value, or a reference-data file, **not** a hardcoded rule in the daemon.

### 3.2 Integration Point #1 — The Qualification Decision Gate (CORE CHANGE)

**Location:** `packages/intelligence/src/qualification/goods-qualification.ts`

`determineQualificationDecision()` (verified, lines **319–372**) is the single function that returns `pass | review | reject`. The relevant tail:

```typescript
// goods-qualification.ts:343-371 (verified)
if (input.legalCategory === "goods") {
  return REVIEWABLE_ACCESS_ROUTES.has(input.accessRoute) ? "review" : "pass";
}

if (input.legalCategory === "mixed" &&
    input.goodsSeparability === true &&
    input.goodsDensityScore >= 0.55) {
  return REVIEWABLE_ACCESS_ROUTES.has(input.accessRoute) ? "review" : "pass";
}

if ((input.legalCategory === "mixed" || input.legalCategory === "unknown") &&
    input.goodsDensityScore >= 0.55 &&
    input.goodsSeparability !== false) {
  return "review";
}

if (input.legalCategory === "works" &&
    input.goodsDensityScore >= 0.7 &&
    input.goodsSeparability !== false) {
  return "review";
}

return "reject";
```

**Supporting structures (verified):**
- `categoryForDivision()` (lines 225–239): CPV division 45 → `works`; 14–44 → `goods`; 50–98 → `services`. `classifyLegalCategory()` returns `mixed` when ≥2 distinct categories appear.
- `REVIEWABLE_ACCESS_ROUTES` = {`restricted_tender`, `framework_call_off`}; `REJECTED_ACCESS_ROUTES` = {`direct_award`, `closed_framework_award`, `not_bidable`} (lines 50–59).
- Goods-confidence floor `< 6000` bps → `review` (line 339).

**Why a goods-led supply-and-install tender dies today:** it carries goods CPV (div 14–44) **plus** an installation/services CPV (div 50–98) → `classifyLegalCategory` = `mixed`. With no explicit goods/labour value split, `goodsSeparability` is `uncertain` (not `true`), so the `=== true` branch (line 347) is skipped; it lands in the `review`-only branch (line 355) **at best**, and falls through to `reject` if `goodsDensityScore < 0.55`. There is no path to `pass`.

**Ordering constraint (critical — this forces a two-phase design).** `determineQualificationDecision` is called inside `qualifyGoodsOpportunity` (line 108) at the **early** qualify_lot stage — **before** the Stage 11 landed-cost/labour skills run. So the **cost-based** goods value-share **cannot be an input here**: it does not exist yet (the labour cost that the ratio needs is computed later, and only for candidates that survive qualification). Gating this early function on a *cost-based* `goodsValueShareBps` would be a circular dependency.

**But a contract-value goods-share IS already available early (the missed surface).** `qualifyGoodsOpportunity` already accepts `totalValuePence` + `goodsAddressableValuePence` and calls `computeAddressableValue()` (verified, lines **290–317**), which returns `addressableValuePence`: for `goods` → the whole `totalValuePence`; for `mixed`/`works` **with separability** (`goodsSeparability !== false` and `goodsAddressableValuePence` supplied) → the passed-in `goodsAddressableValuePence`; else `null`. This is exactly the **contract-value goods-share basis** that §5.5 recommends as *superior* to the cost proxy — and it is already partially wired into the output. So when the tender itemises goods vs labour/works value, a contract-value share `addressableValuePence / totalValuePence` is computable **at Phase 1** and is the *preferred* dominance basis; only when `goodsAddressableValuePence` is absent does the pipeline fall back to the Phase-2 cost proxy. The change therefore splits across two phases (with Phase 2 used only when the early contract-value basis is unavailable):

- **Phase 1 — early (inside `determineQualificationDecision`):** stop auto-*rejecting* goods-bearing mixed/works. Add a branch (after line 353, before the line-355 branch — re-reading the verified 319–372 body, this sits between the separable-mixed `pass` branch and the `mixed|unknown → review` branch, exactly as sketched) that *provisionally admits* such a contract to **`review`/pending** — purely on "is there a real goods component?", with **no** cost-based value-share. This lets it survive into Stage 11. The existing separable-mixed `pass` branch (line 347) should likewise be **downgraded to defer to Phase 2** *unless* the early contract-value share is already ≥ floor, since it currently passes on density alone and the value-share supersedes it.

`GOODS_PRESENCE_FLOOR` maps directly onto the existing `goodsDensityScore` — which is **text-signal-based**, not cost-based: `computeGoodsDensityScore` (verified, lines **264–288**) starts from a per-category base (`goods` 0.85 / `mixed` 0.6 / `works` 0.3 / `services` 0.15 / unknown 0.45) and adjusts by mention counts (`physicalGoodsMentions ×0.05`, `quantityMentions ×0.04`, `attachmentSignals ×0.03`, minus `serviceMentions ×0.08`), clamped to [0,1]. So `GOODS_PRESENCE_FLOOR` is a **low** threshold on this existing score (e.g. ~0.30–0.40, well under the current 0.55/0.70 dominance bars) meaning "a real goods component is present" — no new signal needs computing.

```typescript
// NEW Phase-1 branch — provisionally admit goods-led mixed/works (value-share NOT yet available)
if ((input.legalCategory === "mixed" || input.legalCategory === "works") &&
    input.goodsDensityScore >= GOODS_PRESENCE_FLOOR &&   // a real goods component (low bar, config)
    input.goodsSeparability !== false) {
  return "review";                                       // pending; dominance decided in Phase 2
}
```

- **Phase 2 — post-landed-cost dominance gate (NEW, separate from the early function):** once Stage 11 has produced the labour + permits cost, compute `goodsValueShareBps` and apply the dominance floor. This lives **at/after the margin gate / decision-synthesis step** — the same post-cost position the gross/net margin gates already occupy — *not* inside the early qualification function:

```
if goods_value_share_bps >= GOODS_DOMINANCE_FLOOR_BPS  → PASS (REVIEW on a restricted route)
else                                                    → REJECT (labour-dominant / effectively service-only)
```

`GOODS_PRESENCE_FLOOR` (Phase 1, low — "has goods at all", expressed against `goodsDensityScore`) and `GOODS_DOMINANCE_FLOOR_BPS` (Phase 2, ~5500–6000 — "goods dominate") are **both config**, the operator's new strategy knobs. The Phase-2 value-share is a **cost-based proxy**; when the early **contract-value** share (`addressableValuePence / totalValuePence`) is available it is preferred and can settle dominance at Phase 1 — see §5.5 basis caveat. This two-phase split is the bridge between the two halves of this feature.

### 3.3 Integration Point #2 — The Description-Quality Service Gate (SECOND, EASILY-MISSED CHANGE)

**Location:** `packages/intelligence/src/customs/description-quality.ts`

`gateDescriptionQuality()` (verified, lines 100–113) fires a hard `reject_service` on a regex:

```typescript
// description-quality.ts:108-113 (verified)
if (isServiceDescription(normalizedText)) {
  return { kind: "reject_service", reason: "service_description_not_physical_goods" };
}
```

```typescript
// description-quality.ts:~361 (reported by agent)
function isServiceDescription(text: string): boolean {
  return /\b(consulting|installation|maintenance|managed|repair|services?|support|training)\b/.test(text);
}
```

**This is the trap.** Even if §3.2 is fixed, the word "installation" or "maintenance" anywhere in a description triggers an *unconditional* reject here — at the per-candidate description level, independent of CPV. "Supply **and installation** of steel shelving" dies on this regex regardless of value-share.

**Required change:** split the gate into *goods-led-mixed* vs *pure-service*. Concretely: if the description contains goods/supply signals (head noun, quantities, "supply", "provision and installation of <goods>") **as well as** an installation/maintenance term, classify as `goods_led_mixed` (continue, flag for the value-share rule downstream) rather than `reject_service`. Keep the hard reject only for pure-service patterns ("consultancy", "managed service", "training", maintenance/repair with **no** goods head noun). This is the more delicate of the two filter changes and needs heavy negative-case testing (Appendix A).

**Reuse the existing verdict taxonomy — don't invent a parallel one.** `gateDescriptionQuality` already returns a `DescriptionQualityVerdict` discriminated union (verified, lines **23–36**) that *already* has bundle-handling variants:

```typescript
// description-quality.ts:23-36 (verified)
export type DescriptionQualityVerdict =
  | { kind: "accept"; attributes: ExtractedAttributes }
  | { kind: "reject_generic"; reason: string; missingArchetypeFacts: string[] }
  | { kind: "reject_service"; reason: string }
  | { kind: "reject_bundle_unsafe"; reason: string; markAs: "mixed_manual" | "gir_3_candidate" }
  | { kind: "split_safe"; subDescriptions: RawDescription[] };
```

The service-gate split should **add a `goods_led_mixed` variant** to this union (e.g. `{ kind: "goods_led_mixed"; installationTerms: string[]; goodsHeadNoun: string }`) and downgrade the matching `isServiceDescription` branch to emit it, rather than building a separate mechanism. The pre-existing `split_safe` / `reject_bundle_unsafe` variants show the gate is already bundle-aware, so the new variant is a natural extension, and downstream consumers already `switch` on `kind`.

(The unused field is a fine *fallback* if a zero-migration MVP is wanted, but explicit fields are cleaner for the 3-point band + confidence + UI.) The rollup edit is one additional `.saturating_add()` term **in each of the two construction functions** (domestic and import), not one.

### 4.4 Recommended data strategy (answers the "what engine?" question)

**Hybrid, heavily weighted to a curated table — option (a) for ~95% of triage.** Reasoning:
1. **Curated regional rate matrix** = the engine core: `trade × region(11) × tier(labourer/skilled/specialist) × {hourly, day_rate, callout_min, vat_flag}` + provenance + last-refreshed per cell. Seed from HaMuch + tradedayrates + ConcreteMath, sanity-check against JIB/ONS floor.
2. **Region = multiplier on a Midlands baseline** (multipliers are stable and source-consistent).
3. **Refresh quarterly/semi-annually**, not per estimate — labour rates move slowly; the meaningful step-changes are the **April NLW uplift** and **JIB annual awards**.
4. **Do NOT live-scrape per estimate:** negligible freshness gain, Checkatrade/MyBuilder bot-management breakage risk, noisy single listings, and triage must be fast/cheap.
5. **Light live/manual lane only for:** access-equipment hire (genuinely volatile, callback-priced → model as banded ranges refreshed against 2–3 named suppliers) and high-value bids where a human wants a check.
6. **Always carry VAT + "what's excluded" flags** and a ±20% contingency.

### 5.2 Component Design

**Component A — Installation-Requirement Extractor.** Lightweight: during product extraction / reclassify, detect installation/maintenance intent from CPV + description and emit an `InstallationRequirement` onto the candidate's `critical_attributes_json` (`requires_installation`, `installation_scope`, `maintenance_schedule`, `site_access`, `at_height`, `estimated_units`, `uk_region` derived from delivery postcode). Can start rule/keyword-based; upgrade to the extraction skill later.

**Component A2 — Installation Profile Resolver (the goods → trade + equipment mapping). THE GENERALIZATION MECHANISM.** This is what lets the engine work for *any* installable good, not just lights. It mirrors the existing `match_archetype` pattern (which drives search strategy per product) with an **installation archetype/profile** that drives labour resolution. Three layers:
1. **Curated installation-profile catalogue** — config JSON (extensible like the rate table), keyed by goods archetype / CPV family → `{ required_trades[], hours_per_unit, crew_size, equipment_rule, complexity, tier }`. Seeded with common archetypes (flat-pack furniture, wall-fixed shelving, glazing/windows, electrical-fixture/lighting, signage, fencing, playground, CCTV/security). See Appendix B.
2. **LLM inference fallback inside the skill** for archetypes not in the catalogue — the agent reads the tender + goods description and proposes trade(s) + rough hours + equipment, **constrained to the trades the rate table knows** (so it cannot invent a nonexistent trade) and flagged lower-confidence. This is the core reason labour is an *agent skill*, not deterministic-only code.
3. **Overlay validation** (Component F) sanity-checks the resolved trade/hours/equipment for plausibility (e.g. "windows → electrician" or implausible hours → flag).

The resolver maps **goods → which trade(s) + equipment**; the rate table (Component C) then *prices* that selection with the regional multiplier. Worked examples: windows → `glazing_installer` (~1.5–2.5 h/window, 2-crew, MEWP if upper-floor); CCTV → `security/electrical installer` (per-camera + cabling, MEWP if at height); festive lights → `electrician + labourer + operated MEWP + traffic management`. **Scope-guard interaction (two distinct mechanisms — do not conflate):** (a) *labour/civils-heavy* goods (e.g. traffic signals = highway electrician + NRSWA + civils) are caught by the **Phase-2 dominance floor** — estimable, but they fail the goods-value-share test automatically. (b) *bespoke / no-list* goods (e.g. made-to-measure windows) are typically **goods-dominant**, so the dominance floor would *pass* them; they must be caught by a separate **no-list/bespoke flag**. ⚠️ The L0 no-list is **not** code-enforced today (§3.8), so this flag is a *new* lightweight check this feature must add (no-list CPV match → reason `out_of_scope_category`; bespoke/made-to-measure keyword → `out_of_scope_bespoke`) routing to **review** (not auto-reject, since text-based bespoke detection is fuzzy). Without it, a goods-dominant bespoke contract would silently pass. So the engine generalizes (the resolver estimates anything) while two *separate* guards keep discipline — the dominance floor (automated, economics) and the no-list flag (new, category/bespoke).

**Component A3 — Permits & Traffic-Management Cost + Responsibility Resolver. (Often the biggest swing factor for public-realm work.)** Public-realm/highway/at-height jobs frequently require a Temporary Traffic Regulation Order (TTRO), street-works permit, lane rental (London TLRN / Kent), parking-bay suspensions, scaffolding/highway licences, and **physical** traffic management (signs/barriers/operatives) — which the TTRO fee explicitly *excludes*. **The cost can rival or exceed the labour+equipment cost**, and **who pays is contract-specific**: the contracting authority (when it is the highway authority, e.g. a council on its own streets) may make/waive the TTRO and include TM, OR the contractor must apply, pay fees, and provide TM. This is stated in the ITT/spec but is **not knowable at first-pass triage**. Modelling:
- A distinct **`PermitTrafficMgmtLineItem`** cost component (separate from labour and equipment).
- A **`permit_responsibility`** flag on the installation requirement: `authority_provided | contractor_provided | shared | unknown`.
- **Conservative default:** when unresolved, treat as `unknown` → include a conservative permit+TM band in the `high` estimate, set the `base` to a mid value, and raise `PERMIT_RESPONSIBILITY_UNKNOWN`. This mirrors the customs engine's "conservative bounding + flag for manual review" pattern.
- **Resolution path:** extract the permit/TM responsibility from tender documents at the deeper (decision-grade) assessment stage; once resolved to `authority_provided`, drop the band to ~£0; once `contractor_provided`, price it from the seed bands (Appendix B) keyed off the work location (lane-rental zone? parking suspension? closure scale?).
This component is also the single largest source of triage-estimate *uncertainty width* for high-street work, so it dominates the low/high spread, not the point estimate.

**Component B — UK Installation-Labour Estimate Skill** (`skills/landed-cost/uk-installation-labour-estimate`). Receives the candidate + installation requirement + region; invokes the Permits & Traffic-Management Resolver (Component A3) for public-realm jobs; invokes the Installation Profile Resolver (Component A2) to determine trades + equipment; looks up the curated rate table; decomposes into `LabourLineItem`s (trade, hours, rate) + optional `AccessEquipmentLineItem`s + `PermitTrafficMgmtLineItem`s; returns a 3-point GBP-pence estimate + confidence + evidence/warnings/blockers. It mirrors the freight skill's result-envelope *shape*, but **not** its interaction profile: the freight skills are `pty_interactive` + `requires_cdp: true` (browser-driven), whereas this skill reads skill-local reference tables and does bounded LLM archetype inference with **no browser**. The honest fit is **`interaction_profile: http_public`** (`requires_cdp: false`) — the same profile `simple-fx-lookup` uses (note: `hmrc-customs-classification` is actually `pty_interactive`/CDP, so it is *not* a valid analogy here, contrary to an earlier draft). `skill_lint.rs` accepts exactly three profile values — `pty_interactive`, `http_public`, `headless_contract` — so `http_public` is valid; a `headless_contract` choice would also pass lint and is defensible *only if* the team treats labour as a pure contract-mode compute skill, but `headless_contract` is otherwise the **overlay/manifest-generation** profile, so `http_public` is the cleaner fit for an operational worker. (Component F, the *overlay*, IS correctly `headless_contract`.)

**Component C — Curated Rate Tables (skill-local, read by the skill — NOT a daemon loader).** There is **no `data/reference/` directory, no startup reference-JSON loader, and no "freight provider config" loaded at daemon start** to parallel today — freight skills fetch live, and existing seed/reference data lives as cassette fixtures under `tests/fixtures/cassettes/` (e.g. `l5/fx/hmrc-monthly-current.json`). Rather than establish a brand-new daemon-side reference-loading convention, **ship the rate tables inside the skill directory** — `skills/landed-cost/uk-installation-labour-estimate/reference/uk-regional-labour-rates-<ver>.json` (+ access-equipment bands, installation-profile catalogue, permit/TM bands) — read by the skill itself, since it is the skill (not the daemon) that needs the rates. Versioned; quarterly refresh = new file + `rate_table_version` bump in the skill `config_json`. This keeps the rates modular **and** avoids net-new daemon infrastructure. (A shared `data/reference/` dir + daemon loader remains a possible future refactor if other skills come to need the same tables, but it is *not* required by this feature and would be net-new work — see ADR-004.)

**Component D — Goods-Value-Share calculator.** Pure function: `goods_value_share_bps = goods_landed_cost ÷ (goods_landed_cost + non_goods_cost)` where `non_goods_cost = install_labour + permits_tm` (integer-pence, bps out). It is a **cost-based proxy** for the buyer's goods-vs-service scope split — see the §5.5 basis caveat. Lives next to the coverage rollup; feeds the new qualification branch.

**Component E — Qualification changes.** The new goods-led-mixed branch (§3.2) + the service-gate split (§3.3).

**Component F — Validation overlay** (`skills/validation/overlay-labour-cost`, Phase 2): semantic sanity — hours plausible for scope, rate within regional bounds, postcode valid, equipment proportional.

### 5.5 Goods-Value-Share & Decision Flow

```
goods_landed   = supplier + freight + duty + import_vat                 (existing)
install_labour = labour_base + access_equipment                         (NEW)
permits_tm     = ttro + lane_rental + parking_suspension + physical_tm   (NEW; 0 if authority_provided)
non_goods      = install_labour + permits_tm
total          = goods_landed + non_goods
goods_value_share_bps = round(goods_landed * 10000 / total)
# permits_tm sits on the NON-GOODS side of the ratio: a permit-heavy high-street
# job correctly pushes goods_value_share DOWN, so it can fail the dominance floor.

# This is the PHASE-2 gate — runs AFTER Stage 11, once labour+permits cost exists.
# (Phase-1 early qualification only provisionally admits goods-bearing mixed to "review".)
decision:
  if pure-service (no goods head noun, services CPV only) → REJECT      (Phase-1 service gate)
  if goods-led mixed AND goods_value_share_bps ≥ GOODS_DOMINANCE_FLOOR_BPS → PASS/REVIEW
  else (labour-dominant) → REJECT (effectively service-only economically)
margin gate: net_margin uses economic_landed_cost INCLUDING install_labour + permits_tm
```

`GOODS_DOMINANCE_FLOOR_BPS` default **5500–6000** (55–60%), configurable. This single config value is the operator's new strategy dial — raise it to be conservative (only goods-heavy installs), lower it to chase more install-heavy work.

**Basis caveat (important — the share is a proxy, not an exact scope split).** This value-share is computed on *Sorellon's landed cost*, which is a **proxy** for the buyer's goods-vs-service *scope* split — not the split itself. Because Sorellon sources goods cheaply (multi-country) but pays UK-market labour, the cost-based share **systematically understates** how goods-dominant a contract really is: a contract that is ~80% goods by the buyer's value can compute as ~55–60% by Sorellon's cost, risking a **false reject**. This conflates two questions the spec must keep separate — *eligibility* ("is this fundamentally a goods contract Sorellon may bid?", best judged on scope / contract-value) vs *economics* ("is there margin once UK labour is paid?", which the margin gate already owns on a cost basis). Mitigations: (a) where the tender itemises goods vs labour/works value, or a contract-value / quantity goods-share is derivable, **prefer that** over the cost proxy — and this is **not hypothetical**: `computeAddressableValue()` (goods-qualification.ts:290–317) already produces a contract-value `addressableValuePence` at Phase 1 (whole `totalValuePence` for `goods`; the supplied `goodsAddressableValuePence` for separable `mixed`/`works`), so the contract-value share `addressableValuePence / totalValuePence` is available *before* Stage 11 whenever the tender supplies the split. The spec should make the decision logic **prefer this early contract-value share when present, and fall back to the Phase-2 cost proxy only when `goodsAddressableValuePence` is absent**; (b) route near-floor cases to **review**, never auto-reject, so a human catches false negatives; (c) keep the floor a config dial. The MVP still needs the cost proxy because it is the only thing computable when the tender does not itemise — but it is the *fallback*, not the primary basis, and must be labelled a proxy, not treated as ground truth.

**Recurring-maintenance basis (capital event, not capitalised term).** Summing a multi-year maintenance contract's labour over its full term would almost always swamp the one-off goods value and force a reject — which would defeat the operator's explicit intent to pursue supply-and-maintain work. Therefore the dominance test is assessed **only on the initial supply+install capital event** (goods + one-off install vs that event's labour/permits). Ongoing maintenance is **not** capitalised into the dominance denominator; it is handled as a **separate, annualised per-period margin check** that the operator sees but which does not by itself disqualify a goods-led supply. (This supersedes the looser "capitalised maintenance" wording elsewhere.)

### 5.6 Error / Degradation Strategy

Mirror the freight skill: a `blocked` labour result (no rate cell, unknown region, implausible scope) does **not** fail the pipeline — it yields `install_labour` with low confidence and forces the candidate to `review` rather than `pass`. Confidence aggregates into the estimate's `commercial_estimate_confidence_bps` (min of components). New warning codes: `LABOUR_REGION_UNKNOWN`, `LABOUR_SCOPE_UNRESOLVED`, `ACCESS_AT_HEIGHT_ASSUMED_MEWP`, `MAINTENANCE_TERM_ASSUMED`, `RATE_TABLE_STALE`, `PERMIT_RESPONSIBILITY_UNKNOWN` (permits/TM band included in `high` pending ITT extraction), `LANE_RENTAL_ZONE` (London TLRN / Kent — per-day charges may apply), `TTRO_LEAD_TIME_RISK` (12-week notice may exceed bid/delivery window).

### 6.4 Validation Strategy — Scenario-Based Test Runs (the heart of the plan)

The operator explicitly asked for "a clear validation strategy with real scenario-based test runs." Principle: **every behavioural claim is pinned by a named, runnable test with an expected verdict.** Four classes (full corpus = Appendix A; **operationalised into runnable E2E manifests in Appendix E**):

1. **Acceptance** — goods-led install/maintenance that MUST now pass/review (Scenarios 1, 2, 3, 4, 9).
2. **Negative controls** — service-only / labour-dominant that MUST still reject (Scenarios 5, 6, 7).
3. **Regression controls** — pure-supply that MUST still pass unchanged (Scenario 8).
4. **Scope-boundary controls** — costable but excluded by the dominance floor or no-list flag (Scenarios 10, 11).

Acceptance gate for promotion past Canary: **100% of negative + regression controls hold, acceptance precision ≥ the agreed floor**, evaluated through the calibration fixture corpus + `skill_canary_harness.rs` — *not* a DB-backed `evaluation_*` harness (it does not exist). The Christmas-lights case (Scenario 1) is the **engine-acceptance hard assertion**: base labour must land in the §4.5 NW band (£2,100–2,650 = **210000–265000 pence**) or the rate table / scope model is wrong.

## 7. Architectural Decisions (ADRs)

### ADR-001 — Filtering rule = goods value-share threshold (not CPV-only, not lenient)
**Status:** Accepted (operator-selected).
**Decision:** Accept a mixed contract iff computed `goods_value_share_bps ≥ GOODS_DOMINANCE_FLOOR_BPS` (config, default 5500–6000); else reject. **Options:** A value-share (chosen) — most defensible, reuses the cost engine; B CPV-primary+labour-cap — simpler but CPV is imprecise for mixed; C lenient goods-present — maximizes pool but wastes downstream effort. **Consequence:** requires the labour engine to exist before the filter can be trusted (the two halves ship together). **Known limitation:** the share is computed on Sorellon's *cost* as a proxy for the buyer's goods-vs-service *scope* split; cheap multi-country sourcing understates goods-dominance, so near-floor cases must route to `review` (not auto-reject) and a contract-value/quantity basis is preferred where the tender provides it (see §5.5 basis caveat). **User input:** resolved.

### ADR-002 — Labour engine = a landed-cost skill (not inline Rust, not external service)
**Status:** Accepted. **Decision:** implement as `skills/landed-cost/uk-installation-labour-estimate`, **loaded transiently via `load_skill(...)` and invoked sequentially inside `run_landed_cost_live_loop` (after FX, before decision synthesis)** — mirroring how the existing freight/customs/sizing/FX landed-cost skills are integrated. **Decision (corrected):** these skills are **not** registered in `registry.rs` `builtin_definitions()` (that registry holds only procurement/marketplace sources), and the group is **not** chained via `next_job_kind`; so **no `registry.rs` edit and no job-runner chaining are needed** — the work is a `load_skill` call + a sequential invocation in the live loop. Promoting landed-cost skills into the registry would be a separate refactor, out of scope here. **Rationale:** maximum reuse of the existing landed-cost-loop/skill-runner/promotion/validation machinery; honours the modularity mandate; keeps daemon edits surgical. **Consequence:** labour estimation reuses `run_landed_cost_skill`'s retry/result-contract/timeout handling for free.

### ADR-003 — Add explicit labour fields (don't silently overload `uk_final_mile_cost_gbp_pence`)
**Status:** Accepted. **Decision:** add `installation_labour_cost_gbp_pence` (+low/high/confidence) and sum into `economic_landed_cost_gbp_pence`; keep the unused field as a zero-migration fallback only. **Rationale:** clarity, 3-point band, UI/manifest needs a named line. **Trade-off:** one small migration vs reusing a column.

### ADR-004 — Curated rate table + quarterly refresh (not live scrape, not paid feed)
**Status:** Accepted. **Decision:** versioned JSON reference files **shipped inside the skill directory** (`skills/landed-cost/uk-installation-labour-estimate/reference/*.json`) and read by the skill itself — **not** under a `data/reference/` dir loaded by the daemon (no such dir or startup reference-loader exists today; DRIFT-corrected, see §5.2-C). Seeded from HaMuch+tradedayrates+ConcreteMath, region-as-multiplier, refreshed quarterly; access-equipment as banded ranges. **Rationale:** §4.4 — slow-moving rates, anti-bot risk, triage needs central tendency not live quotes; skill-local files keep the data modular without inventing net-new daemon reference infrastructure. **Trade-off:** rates can lag (mitigated by `RATE_TABLE_STALE` + NLW/JIB step-change awareness); a shared `data/reference/` + daemon loader is a possible future refactor (net-new work) if other skills need the same tables. BCIS/SPON's cited for methodology, not licensed.

### ADR-005 — Goods-dominance threshold is config, not a literal
**Status:** Accepted. **Decision:** `GOODS_DOMINANCE_FLOOR_BPS` lives in a strategy / qualification-config constant (it gates at decision synthesis; it is **not** a landed-cost-source `config_json`, since those skills aren't registry-bound — §3.6/ADR-002). **Rationale:** it is the operator's primary new strategy dial; the platform was explicitly designed so contract strategy is data, not code.

### ADR-006 — Category breadth = "low-reg only", enforced via gold-set + docs
**Status:** Accepted (operator-selected). **Decision:** add festive/LED lighting, signage, fencing, playground/outdoor, blinds, shelving/racking (wood/plastic), + install on existing furniture/PPE; **metal shelving split out** for trade-remedy; no biocidal/medical/chemical. Enforced by adding gold-set cases + updating `layer-0-gold-set-evaluation.md §1.6`, per the existing expansion rule. **Consequence:** each new category needs its own gold-set validation before production. **Note:** because the no-list is not code-enforced today (§3.8), this feature also adds a lightweight runtime **no-list/bespoke flag** (CPV/keyword → review) so goods-dominant no-list items don't slip through the dominance gate; the gold-set + docs remain the source of truth for the category set.

## 10. Open Questions

### Requiring operator input (non-blocking; sensible defaults proposed)
1. **Goods-dominance default %.** Proposed 55–60%. Lower = more install-heavy work admitted. *Recommendation: start 60%, tune against gold-set.*
2. **Recurring-maintenance default term** when the notice doesn't state one (frameworks often open-ended). *Recommendation: assume 1-year visible term + `MAINTENANCE_TERM_ASSUMED` warning.*
3. **Operated vs self-drive MEWP default.** *Recommendation: operated (no in-house IPAF assumption) — conservative, higher cost.*
4. **Should "review" mixed contracts still appear in the desktop queue, or only "pass"?** *Recommendation: show "review" with the labour + permit breakdown so the operator can manually accept/reject.*
5. **Default `permit_responsibility` at triage.** Proposed `unknown` → include conservative permits/TM band in the `high` estimate + `PERMIT_RESPONSIBILITY_UNKNOWN` flag, resolved by ITT extraction at decision-grade stage. *Recommendation: accept; never assume the authority pays.* Sub-question: should the engine attempt to **auto-extract** permit responsibility from tender documents (an extraction-skill upgrade), or always leave it for operator review? *Recommendation: operator review in MVP; auto-extract in Phase 2.*
6. **No-list/bespoke flag — auto-reject vs review.** Text-based bespoke detection is fuzzy, so auto-rejecting on it risks false negatives. *Recommendation: route to **review** with the exclusion reason by default, and auto-reject only on a high-confidence no-list **CPV** match (e.g. medical/chemical CPV families). Confirm the policy + the bespoke keyword set at spec stage.*

### Requiring further research (Phase 2)
1. Sub-contractor quote ingestion as `quote_class = installer_quote` (turn a real UK installer quote into evidence that overrides the table estimate).
2. Traffic-management / pavement-licence cost sub-model for highway/high-street jobs (currently a flat band).
3. Whether to auto-derive `at_height_m` / MEWP class from tender attachments (drawings) — likely an extraction-skill upgrade.
4. **Goods-share basis — cost-proxy vs contract-value/quantity.** MVP uses the cost proxy (the only thing computable when the tender doesn't itemise). The spec should define when/how to use a contract-value or quantity basis, and how to detect an itemised goods/labour split in tender text, to reduce the false-reject risk flagged in §5.5.
5. **Maintenance capital-vs-opex split.** Confirm the rule that dominance is judged on the supply+install capital event with maintenance handled as a separate annualised per-period margin check (not capitalised into the denominator), and decide how multi-year maintenance margin is surfaced to the operator.

### Independent pressure-tests (raised by this improvement pass — resolve at spec stage)
1. **Net-margin regression on already-passing mixed contracts.** Adding `install_labour` into `economic_landed_cost_gbp_pence` changes the **net-margin gate input** for *any* candidate that now carries an installation requirement — including separable-mixed contracts that **already** reach Stage 11 and pass today (treated as goods-only cost). Such a contract could flip from pass → review/reject purely because labour is now priced. This is *intended* for goods-led installs, but it is a **behavioural change for the existing flow**, not just the newly-admitted one. The gold-set must include a "previously-passing separable-mixed-with-install-CPV" case to measure the shift, and the spec must decide whether labour is added only when an `InstallationRequirement` is actually extracted (so pure-goods candidates are untouched — confirmed by Scenario 8's "labour = 0" expectation).
2. **Backfill / recompute of already-assessed processes.** Processes assessed *before* this ships have `landed_cost_estimates` rows with no labour component and `pipeline_assessments` with no `goods_value_share_bps`. Decide: leave historical rows as-is (labour = NULL/0, value-share absent) vs trigger a recompute sweep. A recompute would re-run Stage 11 labour for in-scope historical candidates — non-trivial, and interacts with the `schema_epoch` bump (§9.3). MVP recommendation: additive columns default to NULL/0; no forced backfill; new assessments only.
3. **Phase-2 gate needs goods-only landed cost *separately* from the labour-inclusive total.** The dominance ratio is `goods_landed ÷ (goods_landed + labour + permits)`. Once labour is summed into `economic_landed_cost_gbp_pence`, the gate must still be able to read the **goods-only** sub-total (supplier + freight + duty + import_vat) to form the numerator. Confirmed feasible: the import rollup already computes that sub-total before the labour add, and the new explicit `installation_labour_cost_gbp_pence` / `permit_traffic_mgmt_cost_gbp_pence` fields let the gate subtract them back out — but the spec must **persist the goods-only sub-total or the labour/permit line items** so the ratio is reconstructable at the decision-synthesis step, not only the summed total.
4. **Recurring-maintenance per-period margin may not fit the current schema.** §5.5 says maintenance is a *separate annualised per-period margin check*, not capitalised into the dominance denominator. But `LandedCostEstimate` / `PipelineAssessment` model a **single capital-event** estimate; there is no per-period / per-visit margin entity today. Decide at spec stage whether the per-period maintenance margin is (a) squeezed into metadata fields on the existing assessment, or (b) needs its own entity (`MaintenancePeriodEstimate` keyed by visit cadence × term). Leaning (b) for honesty, since (a) risks overloading the capital-event row with multi-year semantics it wasn't designed for.
5. **Adversary-architect view — what breaks first.** The two softest seams: (i) the **service-gate regex split** (§3.3) — zero current coverage, fuzzy text heuristics, and the failure is *silent* (a service-only contract admitted reads as a "win" until a human notices); (ii) the **cost-proxy false-reject** (§5.5) — cheap multi-country goods sourcing systematically understates goods-dominance, so a genuinely goods-led contract can be wrongly rejected and *never surface* to be noticed at all. Both argue for: default-to-`review` over hard verdicts, the contract-value basis whenever available, and decision-logging so rejects are auditable.

### Assumptions made
1. **CPV codes are present** on most notices (verified they're stored via `notice_cpv_codes`). If absent, fall back to description-only classification (lower confidence → review).
2. **Delivery location is extractable** for region. If not, default to national baseline (multiplier 1.0) + `LABOUR_REGION_UNKNOWN`.
3. **Festive/signage/fencing are low-reg.** Holds for product compliance; labour-side regs are subcontractor/post-win.
