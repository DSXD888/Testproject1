## What the Push Prompt Does

The push prompt is a **compact continuation nudge** (~75-100 lines, 9 sections) used during execution to:

- Re-orient an agent who has been working on something else and is now joining L4 work
- Continue a paused L4 session after a context reset
- Onboard a fresh agent quickly (when the full kickoff is overkill)
- Re-state the work loop in compact form for an agent who already knows the basics

The push prompt is reused continuously across multiple continuation sessions. It must NOT contain stale instructions. It must always reflect the latest:
- Bead CLI invariants (`br` not `bd`, `bin/br-sync` not `br sync`)
- AgentMail project key
- Verification commands (Stage Validation Test Gate)
- Work loop steps
- Critical contracts

## When to Use the Push (vs Kickoff)

| Scenario | Document |
|---------|---------|
| Fresh agent, no prior L4 context | **Kickoff** (full onboarding) |
| Agent worked on L1/L2/L3 before; now picking up L4 | **Push** (compact re-orient) |
| Agent paused mid-bead and is resuming | **Push** (re-orient, then resume bead) |
| Agent finished one bead and looking for next | **Push** (re-orient, then `br ready`) |
| Mid-execution swarm needs to coordinate | (use AgentMail directly; push prompt unnecessary) |

## Mandatory Sections in the Push Prompt

(All 9 sections must be present. They are generated by step 10.)

### 1. Re-Orient
- Re-read AGENTS.md
- Feature: L4 Shared Visibility — sync engine + web portal + validation enforcement
- SOT paths (spec / strategy / TDD / bootstrap)
- "Your work orders are beads: `br ready --label layer-4 --json`"
- AgentMail registration (compact: project key + macro_start_session)

### 2. Core Contracts (compact)
- Push protocol transactional + atomic (single RPC, partial-apply forbidden)
- Equal-version retry — 4 cases
- Pull-before-push at startup
- CAS with command ledger
- Writer fencing (`writer_epoch`)
- Schema epoch guard
- Provisional promotion for enforcement slices
- Web read-only is a security boundary
- Single-edit chokepoints

### 3. Bead Completion Policy (compact, firm)
- Every bead fully completed before moving on
- Complete = code + tests + checks + committed + announced + reservations released + bead closed + .beads/ pushed
- If blocked: diagnose, fix yourself, escalate via AgentMail only if blocker is in another agent's code

### 4. Work Loop (compact, ~10 lines)
1. Check inbox (`fetch_inbox`) → acknowledge messages
2. `br ready --label layer-4 --json` → pick highest-priority ready bead
3. Read bead FULLY → study target files
4. CLAIM: `br update <id> --status=in_progress` + `file_reservation_paths(...)` + `send_message(to=["<peers>"])`
   (peers from `list_contacts` — NEVER "broadcast")
5. IMPLEMENT: TDD — extend tests first, then code. Implement ALL of it. No mid-way commits.
6. VERIFY: full Stage Validation Test Gate (cargo + bun + Playwright if web)
7. COMMIT: `ubs` + `git add <files>` + `git commit -m "<bead-id>: <desc>"` + `git pull --rebase && git push`
8. COMPLETE: `br close <id>` + `bin/br-sync` + `git add .beads/` + `git commit` + `git push` + `send_message(to=["<peers>"])` + `release_file_reservations`
9. LOOP → step 1
Do not stop to ask what to work on next. Pick the next ready bead.

### 5. Verification Commands (compact)
```bash
# Rust full gate
cargo fmt --check && cargo check --all-targets && cargo clippy --all-targets -- -D warnings && cargo test -p daemon --bin daemon && for t in crates/daemon/tests/*.rs; do cargo test --test "$(basename "$t" .rs)" || exit 1; done

# TS
bun run test && bun run lint && bun run build

# Web e2e (if your bead touches apps/web)
(cd apps/web && bun run test:e2e)

# Pre-commit
ubs $(git diff --name-only --cached)
```

```
Phase 6 (Integration) wires main.rs startup; depends on most prior phases
```

- [ ] AgentMail project key is `/Users/alinaaitova/Desktop/Testproject1` verbatim

- [ ] Sync command is `bin/br-sync` (NOT raw `br sync`)

- [ ] Work loop has the duplicate-claim guard (`br show` + `search_messages`)

- [ ] `apps/web/src/lib/supabase.ts` is the SOLE Supabase boundary in the web app
- [ ] Phase dependency spine accurate (Phase 1 → 2/3/5 parallel; Phase 4 chokepoints; Phase 6 integration)

## When the Push Prompt Becomes Stale

The push prompt becomes stale and MUST be regenerated when:
- The bead corpus changes significantly (new beads added, phase boundaries shift, chokepoint files change)
- The Stage Validation Test Gate changes (e.g., new test command added)
- The AgentMail project key changes (it shouldn't, but if it does, regenerate)
- A core contract is amended via spec change (e.g., new equal-version case added)
- The strategy reorders phases

Regeneration is via re-running step 10 (`/beads-to-execution`).

## Notes for Continuation Agents

When you receive this push prompt:
1. **Do NOT skip the AgentMail registration step.** Even if you think you registered before, run `fetch_inbox` first. There may be messages waiting.
2. **Do NOT trust an old `br ready` cache.** Run it fresh.
3. **Do NOT assume `git pull --rebase` is unnecessary.** Other agents have pushed since you last worked.
4. **Do NOT mix L4 work with L1/L2/L3 maintenance.** Stay scoped to `--label layer-4`.
5. **Do NOT skip `bin/br-sync`** after closing a bead. It's NOT just `br close <id>`. The .beads/ JSONL files must be synced and pushed for other agents to see the closure.
