## The Pipeline: Purpose and Flow

The core purpose is **automated UK public procurement intelligence**: ingest live government contract notices, qualify them, find matching products from supplier sources, estimate landed costs (import duties, freight, margins), and produce opportunity manifests for an operator to approve/reject/watch.

**End-to-end data flow:**

```
1. INGEST         Source → raw_documents + contract_notices (FTS/CF via browser automation)
2. NORMALIZE      contract_notices → canonical procurement_processes
3. RELATE         procurement_processes → process_relations + process_aliases (L3: merge/relate heuristics)
4. PREQUALIFY     notice-grain: expiry check, goods/services classification → qualification_runs
5. ACQUIRE DOCS   notice → tender_document_sets
6. EXTRACT LOTS   notice → notice_lots
7. EXTRACT PRODUCTS  lot → product_candidates + search_profiles
8. SCORE QUOTEABILITY  candidate → quoteability_score_bps
9. PRICE-SIGNAL MATCH  candidate×source → search_attempts + supplier_quotes
10. GROSS MARGIN GATE  candidate → candidate_pricing_assessments (identity→usability→realism gates)
11. LANDED COST   candidate×quote → landed_cost_estimates (HS10 classification, duty, freight, VAT, FX)
12. NET MARGIN GATE  candidate → net margin + coverage floor check
13. MANIFEST      process → manifests (Markdown opportunity narrative)
14. OPERATOR DECISION  process → pending_operator_intents (approve/reject/watch)
```

Each stage writes `process_stage_status` (append-only execution record) and advances `process_stage_heads` (current successful run). Stages have scope grains (process/notice/lot/candidate/candidate_source_pair) with set-replacement or additive commit semantics.

**In the live loop implementation** (`main.rs` lines 3300+), the daemon currently executes this as a single FTS ingestion → fixture-driven pipeline materialization → manifest generation flow, writing all domain tables in one SQLite transaction per process.

# Intent-to-Handoff — Intelligent Handoff Prompt Generator

## Philosophy

This skill transforms raw user intent into a self-contained handoff prompt that a fresh Claude Code session (with ZERO prior context) can execute autonomously.

```
┌─────────────────┐     ┌──────────────────────┐     ┌─────────────────────────┐
│   USER INTENT   │ ──► │  INTELLIGENT RESEARCH │ ──► │   HANDOFF PROMPT (.md)  │
│                 │     │                       │     │                         │
│ "I want to add  │     │ • Discover project    │     │ • MISSION statement     │
│  feature X to   │     │ • Explore codebase    │     │ • File-specific reading │
│  this project"  │     │ • Map architecture    │     │ • Embedded types/APIs   │
│                 │     │ • Scan docs/specs     │     │ • Constraints & rules   │
│                 │     │ • Find conventions    │     │ • Concrete deliverables │
└─────────────────┘     └──────────────────────┘     └─────────────────────────┘
```

The user describes WHAT they want done. The skill figures out HOW to research it, WHAT context is needed, and synthesizes a document that stands completely on its own.

**Key insight**: A good handoff prompt doesn't just list file paths — it embeds the actual type definitions, API signatures, and architectural patterns that the receiving session needs. "Read types.ts" is insufficient. The actual type shapes must be right there in the prompt.

- "Prepare a prompt for a new session to..."
- "Generate a handoff for [feature/task]"

```
Phase 0          Phase 1           Phase 2              Phase 3
PROJECT     ──►  INTENT       ──►  CODEBASE        ──►  DOC & CONSTRAINT
DISCOVERY        CAPTURE           EXPLORATION          SCAN
(auto)           (interactive)     (subagents)          (auto)
```

**Phase 0 — Project Discovery**: Detect project type, languages, framework, docs, and structure. Fully automatic.

**Phase 5 — Self-Verification**: Run the quality checklist. Verify all file paths exist, ensure self-containment, fix issues, and report to the user.
