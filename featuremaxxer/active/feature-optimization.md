### Architecture Tensions to Investigate

The following tensions were identified during codebase analysis. They are NOT questions for you to answer verbatim — they're thinking catalysts that point at the deepest architectural fault lines. The feature doc may have resolved them correctly (good) or may have created downstream problems (better — that's the insight we need).

**Tension 1: Python subprocess in a pure-Rust daemon**
The feature doc proposes Docling (Python) as a subprocess managed by the Rust daemon. The daemon currently manages only Claude CLI subprocesses (also external binaries, but well-defined stream protocols). Consider whether the subprocess management model (process pooling, timeout, health probe) is sufficiently specified. What happens when Docling hangs? When it OOMs on a 500-page document? When the Python environment is corrupt? The feature doc's Open Question #1 identifies three options (sidecar, subprocess, container) but doesn't resolve it. Is the feature doc's implied preference (option b, direct subprocess) actually the right choice given the daemon's existing process supervision patterns?

**Tension 2: Two new job kinds with fundamentally different execution models**
`extract_document_structure` runs as a daemon-internal subprocess (no agent, no PTY, no contract mode). `extract_document_semantics` runs through the standard Agent Adapter as a headless_contract skill. The Job Runner currently treats all jobs as skill executions routed through the adapter. A daemon-internal subprocess job kind is a new execution category that the Job Runner doesn't handle today. How does this integrate? Does the Job Runner need an `ExecutionMode::Subprocess` variant? Or should structural extraction not be a "job" at all, but a daemon-internal function called during the job lifecycle?

**Tension 3: Document acquisition doesn't exist yet**
The feature doc acknowledges (Section 9, Question 6) that the `document-acquisition` skill doesn't exist. The extraction toolkit depends on PDFs being in `raw_documents`. The feature doc suggests testing with manually downloaded PDFs. But the orchestration flow (Section 4, Component 3) describes a cascade from "Document Acquisition job completes" → structural extraction → semantic extraction. If document acquisition is unbuilt, how much of the orchestration flow is speculative? Should the extraction toolkit be designed to work standalone (given a PDF path) rather than assuming the acquisition cascade exists?

**Tension 4: Large document chunking is required but undesigned**
Open Question #4 explicitly flags this: a 100-page document may produce 50k-100k tokens of markdown, exceeding single-agent context. The feature doc says "should be designed before implementation, not discovered at runtime." But the design isn't in the feature doc. This isn't a nice-to-have — it's a hard constraint that affects the semantic skill architecture, the `extraction_scope` field on `document_semantic_extractions`, and the merge strategy for multi-chunk results. This needs a concrete design, not just a flag.

**Tension 5: Extraction granularity vs semantic_extraction_state aggregate**
The `document_extractions` table has a `semantic_extraction_state` that aggregates across all overlays ("worst state"). But what drives the decision about WHICH overlays to run? The feature doc describes document role classification (OCDS metadata, filename heuristics, structural content analysis) but doesn't specify the mapping from role → set of expected overlays. Without this mapping, the aggregate state is meaningless — "complete" relative to what? This mapping belongs in the extraction policy, but the policy design is implied, not specified.

**Tension 6: Non-PDF documents are mentioned but scope-ambiguous**
Open Question #9 mentions XLSX, DOCX, HTML in tender packs. Docling supports them. But the feature doc title is "PDF Extraction Toolkit" and the entire architecture is described in terms of PDFs. Should the toolkit be "Document Extraction Toolkit" from the start? Or is the scope correctly PDF-first with a clear extension path? If PDF-first, what happens when the first XLSX pricing schedule arrives — does the pipeline degrade to notice-text-only extraction?

**Tension 7: Result persistence requires hard-coded daemon logic (CRITICAL FINDING)**
After a skill session completes, the daemon currently has a hard-coded `if skill.metadata.skill_id.starts_with("procurement-ingestion/")` branch at main.rs:1838 that reads the skill's result JSON and calls `persist_ingestion_from_agent_output()` (main.rs:4523) to write rows to database tables. This is NOT dynamic — every new skill family that needs to persist structured results to the database needs a new persistence function and a new dispatch branch. The feature doc doesn't address this at all. The semantic extraction skills produce `result.json` per their `result.schema.json`, but WHO writes the `document_semantic_extractions` rows? Who writes the domain table rows (lots, candidates)? The feature doc's orchestration flow (§4 Component 3) says "Domain table rows written" but doesn't specify whether the daemon does this or the skill does. Given `side_effect_class: none`, the skill can't write to the database directly. The daemon must do it. That means new Rust code: `persist_extraction_from_agent_output()` (or a generic skill result persistence framework). This is a significant integration surface the feature doc misses.

**Tension 8: Testing philosophy tension — mock Docling vs "no mocks" principle**
AGENTS.md and the project's testing philosophy mandate "real E2E agent tests, no mocks/stubs." But the feature doc implicitly and the implementation strategy will explicitly propose a mock Docling subprocess for fast unit tests — because real Docling requires Python + ML models + ~2GB of model files, adding 1-10 seconds per page. A strict "no mocks" interpretation would require every test touching the extraction engine to invoke real Docling. Consider: is a mock Docling subprocess acceptable as long as E2E tests also exist against real Docling? Or should the testing architecture avoid the mock entirely and use a "precomputed fixtures" approach instead (run Docling once, save output as fixtures, test the rest of the pipeline against those fixtures)? The precomputed-fixtures approach is technically not a "mock" — it's a test fixture — and may be more compatible with the project's testing philosophy.

### What Would an Adversary Architect Say?

- "You're over-engineering this. Just send the PDF to Claude Sonnet with a structured output schema. At 300 docs/week the cost is $750/month — less than the engineering time for the Docling integration. The hybrid approach saves money but costs complexity."

## 6. NON-NEGOTIABLES

These decisions are **locked**. Do not question or propose alternatives for these:

### Core Architecture
- **Hybrid two-stage pipeline** (Docling structural + Claude semantic). This is the central design decision.
- **headless_contract mode** for semantic mapping skills. Not PTY.
- **Haiku tier** for semantic mapping (cost-critical). Sonnet only if Haiku proves insufficient.
- **Deterministic caching** by `source_content_hash` + `extraction_engine_version` + `processing_strategy`.

### Skill Architecture
- **Skill-first principle** — skills are SKILL.md + result.schema.json, not daemon code.
- **Same promotion flow** as existing skills (draft → candidate → canary → shadow → stable).
- **Same validation framework** — base validator can validate these runs.
- **Skill loading is dynamic** — no daemon recompilation to add a new SKILL.md. However, **result persistence IS code** — see Tension 7 below. Skill dispatch is dynamic; result handling is not (yet).

### Database
- **Push-owned authority** for `document_extractions` and `document_semantic_extractions`.
- **Sync tracking columns** on all new tables (owner_id, row_version, last_local_seq, stage_run_id).
- **Migration-based schema creation** (new migration file, not inline DDL changes).

### Design Principles
- **Capability, not stage** — the extraction toolkit is available to any skill, not a fixed pipeline step.
- **No mocks in tests** — real E2E agent tests against actual infrastructure.
- **AGENTS.md rules** — no file deletion, no destructive git, Rust 2024 nightly, `#![forbid(unsafe_code)]`.

### Everything else is fair game for questioning.
