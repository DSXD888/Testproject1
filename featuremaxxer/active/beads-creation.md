### Practical consequences

- Build against what EXISTS. Don't assume document-acquisition or other unbuilt infrastructure.
- The extraction toolkit must work given a PDF path/bytes — standalone via `raw_document_id`.
- New tables go in `migrations/0006_pdf_extraction_toolkit.sql`. Schema epoch: **bump to 3** (per strategy §5 — new push-owned entities, new job kinds, new dispatch logic warrant a clean runtime gate).
- New job kinds must integrate with the EXISTING Job Runner dispatch in `main.rs`.
- **Result persistence is NOT automatic.** After a semantic skill runs, the daemon needs hard-coded logic to persist the result to database tables. The existing pattern is `persist_ingestion_from_agent_output()` at `main.rs:4523`, called from a `starts_with("procurement-ingestion/")` branch at `main.rs:1838`. Semantic extraction skills need equivalent persistence: `starts_with("pdf-extraction/")` -> `persist_extraction_from_agent_output()` writing to `document_semantic_extractions` + triggering domain table updates. This is a CRITICAL integration surface.
- `extract_document_structure` is a daemon-internal subprocess job — it does NOT go through `AgentAdapter` or `skill_manifest()`. It needs a separate dispatch branch in `main.rs`.
- `extract_document_semantics` uses standard `headless_contract` via existing `AgentAdapter` — same path as `manifest-generation`.
