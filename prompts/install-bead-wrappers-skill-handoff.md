## 5. The Install Procedure (embed this in SKILL.md "Workflow" section)

The skill's SKILL.md should describe — in language an agent (Claude or Codex) can execute step-by-step — the following procedure. Use exact paths and bash where helpful; mark which steps fail-soft vs fail-hard. Insert "CHECKPOINT — report progress" markers between major phases so the user has visibility.

```bash
# ----- Setup vars -----
PROJECT_ROOT="$(git rev-parse --show-toplevel)"   # fail-hard if not a git repo
PROJECT_NAME="$(basename "$PROJECT_ROOT")"        # human-readable name for `am guard install`
SKILL_DIR="<the skill's own directory — see Implementation Notes §6a>"

# ----- Step 1 — Pre-flight (fail-hard if any of these fail) -----
command -v am >/dev/null         || die "am binary not on PATH; install mcp_agent_mail_rust"
test -d "$PROJECT_ROOT/.git"     || die "not a git repo: $PROJECT_ROOT"
curl -s --max-time 3 http://127.0.0.1:8765/healthz | grep -q alive \
                                 || die "agent-mail server not reachable; run: am serve-http --port 8765 &"
[ -n "$AGENT_NAME" ]             || die "AGENT_NAME env var not set"
test -f "$SKILL_DIR/assets/br-claim"     || die "skill asset missing: br-claim"
test -f "$SKILL_DIR/assets/br-complete"  || die "skill asset missing: br-complete"
test -f "$SKILL_DIR/assets/agents-md-rule-2.md" || die "skill asset missing: agents-md-rule-2.md"

echo "CHECKPOINT 1: pre-flight passed ($PROJECT_ROOT)"

# ----- Step 2 — Install wrappers -----
mkdir -p "$PROJECT_ROOT/bin"
cp "$SKILL_DIR/assets/br-claim"    "$PROJECT_ROOT/bin/br-claim"
cp "$SKILL_DIR/assets/br-complete" "$PROJECT_ROOT/bin/br-complete"
chmod +x "$PROJECT_ROOT/bin/br-claim" "$PROJECT_ROOT/bin/br-complete"
"$PROJECT_ROOT/bin/br-claim"    --help >/dev/null 2>&1 || die "bin/br-claim --help failed post-install"
"$PROJECT_ROOT/bin/br-complete" --help >/dev/null 2>&1 || die "bin/br-complete --help failed post-install"

echo "CHECKPOINT 2: wrappers installed ($(wc -l < $PROJECT_ROOT/bin/br-claim) + $(wc -l < $PROJECT_ROOT/bin/br-complete) lines)"

# ----- Step 3 — Install AGENTS.md Rule 2 (idempotent) -----
AGENTS_MD="$PROJECT_ROOT/AGENTS.md"
if [ ! -f "$AGENTS_MD" ]; then
  cat > "$AGENTS_MD" <<'EOF'
# AGENTS.md

> Guidelines for AI coding agents working in this codebase.

EOF
fi

if grep -q "BEGIN: AGENTS.md Rule 2 (managed by install-bead-wrappers skill)" "$AGENTS_MD"; then
  echo "Rule 2 already present in $AGENTS_MD — skipping (idempotent)"
else
  printf "\n\n" >> "$AGENTS_MD"
  cat "$SKILL_DIR/assets/agents-md-rule-2.md" >> "$AGENTS_MD"
  echo "Rule 2 appended to $AGENTS_MD"
fi

echo "CHECKPOINT 3: AGENTS.md Rule 2 in place"

# ----- Step 4 — Install precommit hook (delegate to `am guard install`) -----
# CORRECT command: `am guard install <PROJECT> <REPO>` (positional args, NOT --project flag)
# Optional flag: --prepush also installs a pre-push hook (skip for default install)
am guard install "$PROJECT_NAME" "$PROJECT_ROOT"
test -x "$PROJECT_ROOT/.git/hooks/hooks.d/pre-commit/50-agent-mail.py" \
  || die "precommit hook not installed by am guard install"

# Verify via am itself:
am guard status

echo "CHECKPOINT 4: precommit hook installed and reporting status"

# ----- Step 5 — Smoke test (no real bead claim — see pre-L5 sanity check handoff for that) -----
cd "$PROJECT_ROOT"
"$PROJECT_ROOT/bin/br-claim" --help    | head -3
"$PROJECT_ROOT/bin/br-complete" --help | head -3
grep -q "RULE NUMBER 2" "$AGENTS_MD"
test -x "$PROJECT_ROOT/.git/hooks/hooks.d/pre-commit/50-agent-mail.py"

echo "CHECKPOINT 5: smoke test passed"

# ----- Step 6 — Report (then STOP — do NOT chain into bead claiming) -----
cat <<EOF
install-bead-wrappers complete in $PROJECT_ROOT.

Wrappers:    $PROJECT_ROOT/bin/{br-claim,br-complete}
AGENTS.md:   $PROJECT_ROOT/AGENTS.md  (Rule 2 present)
Hook:        $PROJECT_ROOT/.git/hooks/hooks.d/pre-commit/50-agent-mail.py (installed via 'am guard install')

Next steps for the user:
  1. Commit the new files: git add bin/ AGENTS.md && git commit -m "chore: install bead wrappers + AGENTS.md Rule 2"
  2. (The hook is git-local; no commit needed for it.)
  3. Run the pre-L5-sanity-check handoff before spawning multi-agent work in this project.
EOF
```

## 6. Implementation Notes (gotchas the agent must handle)

### 6a. SKILL_DIR discovery — CLI-aware

The skill needs to know its own asset path. Two CLI cases:
- Claude: skill dir is `~/.claude/skills/install-bead-wrappers/`
- Codex: skill dir is `~/.codex/skills/install-bead-wrappers/`

The SKILL.md should NOT hardcode either path. Instead, instruct the executing agent to detect via:

```bash
# Detect skill dir from this skill's own path (the agent knows its CLI's skill root):

                       realpath ~/.codex/skills/install-bead-wrappers/SKILL.md)")
```

Or pass the assets via a known env var the CLI sets when invoking skills. Match whatever convention the existing skills use (inspect peer skills' SKILL.md to confirm).

### 6b. Wrappers may have evolved between snapshot and use

The wrappers in `Testproject1/bin/` are the canonical version at the moment this skill is created. If they evolve later (bug fixes, new features), the skill assets become stale. Two mitigations:
- The skill's METHODOLOGY.md should clearly state the snapshot version (e.g., "wrappers snapshot from Testproject1 commit `<sha>` on `<date>`").
- Future skill updates can re-run this handoff: re-copy the canonical wrappers into the skill's assets, bumping the snapshot pointer.

This is acceptable because wrappers don't change often, and any project using the skill will have a working snapshot — they just may not have the latest fixes until the skill is refreshed.

### 6c. AGENTS.md Rule 2 idempotency — the marker matters

The HTML-comment marker (`<!-- BEGIN: AGENTS.md Rule 2 (managed by install-bead-wrappers skill) -->`) is the ONLY signal the install procedure has for "is Rule 2 already there?" If the user manually copies Rule 2 (without the marker) and then runs the skill, the skill will append a SECOND copy — pollution. The METHODOLOGY.md should warn about this, and recommend always letting the skill manage Rule 2 (or manually adding the markers when copy-pasting).

### 6d. `am guard install` semantics (verified)

The `am guard install <PROJECT> <REPO>` subcommand installs a precommit hook at `<REPO>/.git/hooks/hooks.d/pre-commit/50-agent-mail.py`. The hook gets project-specific config baked in via the `<PROJECT>` positional arg — that's the value that ends up in the hook's `PROJECT = "..."` line.

Documented surface (run `am guard install --help` to verify on the user's machine):
```
Usage: am guard install [OPTIONS] <PROJECT> <REPO>

Arguments:
  <PROJECT>    Human-readable project identifier (e.g., the repo basename)
  <REPO>       Absolute path to the repo root

Options:
  --prepush     Also install a pre-push hook (defaults to NOT installing)
  --no-prepush  Explicit opt-out of pre-push (default behavior)
  -h, --help    Print help
```

Idempotency: `am guard install` is safe to re-run — it overwrites the hook with the canonical version and re-stamps the project metadata. Use `am guard status` post-install to confirm. Use `am guard uninstall` to roll back if needed (rollback path documented in METHODOLOGY.md).
